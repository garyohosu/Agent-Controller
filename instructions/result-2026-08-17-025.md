## 2. Task Complexity Router 仕様（`router.py` / `design.py`）

`TaskType`（`models.py`）: `NEW_PRODUCT / NEW_FEATURE / SMALL_FEATURE / BUG_FIX / REFACTOR / DOC_ONLY`。

`RunState.task_type: TaskType | None = None`。**None は「未分類 = 従来のフル経路」** であり、
既存の呼び出し側（`lifecycle.start_run` を直接呼ぶ既存 280 件のテストを含む）の挙動を
一切変えない、意図的な既定値である。

`router.FAST_PATH_STAGES` が指示書 §3.2 の推奨経路をそのまま表に落とす:

```text
NEW_PRODUCT    SPEC -> USECASE -> SEQUENCE -> CLASS -> TESTCASE   (UI は include_ui=True で追加)
NEW_FEATURE    SPEC -> USECASE -> TESTCASE
SMALL_FEATURE  SPEC -> TESTCASE
BUG_FIX        SPEC -> TESTCASE
REFACTOR       SPEC -> TESTCASE
DOC_ONLY       SPEC
```

`router.classify_task_type(request)` は自由文からの保守的な既定分類器。新規製品らしい
手がかりが無く、他のどの分類にも当てはまらなければ **NEW_PRODUCT（フル経路）へ倒す**
（§3.3「不明でも保守的な既定値」）。この自動分類は **公開 CLI (`agent-controller init`) の
入口だけ** で既定適用される。ライブラリの `lifecycle.start_run()` 自体は `task_type=None`
が既定のままで、既存のテスト・呼び出し側には一切影響しない。

### Fast Path の実装

`design.design_stages_for_task_type(task_type)` が `FAST_PATH_STAGES` から
`DocumentStageConfig` の一覧を組み、`graph.wired_handlers` の `design_handler` が
`run.task_type is not None` かつ呼び出し側の明示 `design_stages` 上書きが無い場合にだけ
これを使う。

省いた工程（例: SMALL_FEATURE の USECASE / SEQUENCE / CLASS / UI）は
`design.mark_fast_path_skips()` が **その run で DESIGN に初めて入るときだけ**
`ArtifactStatus.VALID` + `reason="NOT_REQUIRED (fast_path=...)"` として書く。これは
既存の README アーティファクトが `NOT_REQUIRED` を使っているのと同じ形であり、
`CompleteGate.REQUIRED_DESIGN` 側は変更していない。`mark_fast_path_skips` は
「行が既に存在する工程には触れない」ため、resume を挟んでも updated_at が更新後方向へ
動かない（`run_design` / `merge_impacts` は常に呼び出し側が渡した縮小後の `stages` しか
見ないため、上位手戻りが対象外の工程を書き換えることも無い）。`tests/test_router.py::
test_mark_fast_path_skips_only_writes_missing_kinds` で固定した。

TEST / REVIEW / CompleteGate はどの TaskType でも一切スキップしていない
（`tests/test_router.py::test_small_feature_fast_path_skips_docs_but_keeps_test_review_and_gate`）。

## 3. Auto-Recovery 規則（`capability.py` / `worker.py`）

### エラー分類

`capability.classify_worker_error(reason, raw_output)` が既知の手がかり（英語・日本語）から
`WRITE_PERMISSION_DENIED` / `READ_PERMISSION_DENIED` / `TIMEOUT` を割り当てる。
`WORKER_ERROR` を返した Worker が `finding_code` を自己申告していない場合だけ、
`phase_handlers_from_worker` がこの分類で補う（後方互換: 既存の Worker 自己申告は上書きしない）。

`needs-detector` フィールドテストで実際に出た文言
`"SPEC.md and dream.md could not be updated because filesystem writes were denied."` を
パターンの根拠にしている。

### Capability フィルタ

`WorkerCapability`（can_read / can_write / can_review / can_implement / can_answer /
supports_plan_mode / supports_structured_output）を Worker ごとに静的宣言する
（`DEFAULT_CAPABILITIES`。既存の CLAUDE_CODE / CODEX_CLI / GROK / ANTIGRAVITY は全項目
True のままなので、指定しない限り既存挙動は変わらない）。

`phase_handlers_from_worker(..., capabilities=...)` は GENERATE / FIX の候補を
`can_write=True` のものだけに絞る。絞られた候補は **一度も `.run()` を呼ばれない**
（`tests/test_capability.py::test_write_incapable_candidate_is_never_invoked_for_generate`
で `.calls == 0` を直接検証）。Reviewer は元々 read-only のままで、この変更で権限を
広げてはいない。

### 復旧の流れ

```text
候補 1 が WORKER_ERROR/WORKER_RESOURCE_LIMIT
  -> 同一候補への単純再試行はしない（既存実装が元々そうだった。§8 参照）
  -> checkpoint は phase 呼び出し内で 1 度だけ begin() されるため、
     candidate を切り替えても同じ checkpoint のまま rollback する
  -> エラーが TIMEOUT 分類なら、次の候補への指示を shorten_directive() で短縮する
  -> 次候補（can_write を満たすものだけ）へフォールバック
  -> 全候補失敗で初めて WORKER_ERROR を上位へ返す
     (-> トップレベル遷移表により HUMAN_REQUIRED)
```

dirty workspace は `GitCheckpointManager.begin()` が候補ループへ入る前に
`DirtyWorkingTreeError` を投げるため、**Worker を一切呼ばずに** 即座に拒否する。
`git clean` / `reset --hard` / `stash` は今回も追加していない
（`tests/test_capability.py::test_dirty_workspace_is_rejected_without_touching_git`,
`test_dirty_workspace_stops_phase_handler_before_any_worker_is_called`）。

### Recovery Log

`recovery_attempts` テーブル（SQLite、migration v6）に 1 試行 1 行で残す:
`error_code, failed_worker, failed_role, capability_mismatch, fallback_worker,
attempt_number, final_outcome, reason`。`agent-controller recovery --run RUN` で参照できる。

## 11. 既知の制限

- **DOC_ONLY はトップレベル State をスキップしない。** 指示書 §3.2 は
  `SPEC -> REVIEW`（実装工程を通さない）を挙げているが、`transitions.py` の
  `DESIGN + PASS -> IMPLEMENT` は無条件遷移であり、これを DocumentStage 側の
  Fast Path だけで安全に迂回する変更は今回のスコープでは行っていない。現状の
  DOC_ONLY は DESIGN 側で SPEC のみを要求するに留まり、IMPLEMENT / TEST / REVIEW は
  引き続き通る（安全側だが、指示書の理想形より保守的）。
- **§7 の同一Run再利用は Worker の自己申告が無いと作動しない。** 質問を出す側
  （GENERATE/FIX/REVIEW の Worker）が `policy_scope` を自ら申告した場合のみ動く設計
  にした。Controller が自由文の類似度から推測することはしていない。実 AI が
  directive に従って実際に `policy_scope` を返すかは、今回のフィールド回帰の範囲では
  未確認。
- **`classify_worker_error` は文字列一致に依存する。** CLI ごとの終了コードが安定して
  分かるまでの暫定実装。パターンを外すと「本来 fallback すべきなのに分類できない」
  だけなので安全側に倒れるが、検出漏れはあり得る。
- **`classify_task_type` は保守的なキーワード分類器であり、AI/Director による構造化提案
  ではない。** 指示書は「Controller / Director がタスク種別を構造化して提案」を
  想定しているが、今回は Controller 側の決定論的なデフォルト分類器のみを実装した
  （AI 提案経路は将来の拡張点として残す）。
- **NEW_FEATURE の SEQUENCE/CLASS/UI「影響範囲に応じて必要時のみ」を固定集合に
  単純化した。** Controller は決定論的でなければならないため、`FAST_PATH_STAGES` は
  固定表であり、実行時の影響範囲分析で動的に増減する経路にはしていない。追加が
  必要になった場合は既存の UPSTREAM_CHANGE_REQUIRED / 影響範囲分析の経路で
  STALE を足し直せる。
- **Recovery Log はまだ次回の候補順に反映されない。** `recent_timeout_count` 等の
  ランタイム診断を Worker 優先度へ自動反映する学習型ルーターは指示書 §5 の通り
  範囲外のまま。
- **フィールド回帰は SPEC 1 stage・隔離クローンに限定した。** 実際の
  `C:\PROJECT\needs-detector` に対する複数 stage・複数時間規模のライブ実行は、
  実行中の NEEDS-CPF-GATE-002 と衝突するリスクを避けるため今回は行っていない。
