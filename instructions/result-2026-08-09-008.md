## 実装したもの（§1〜§3）

### HUMAN_ANSWER の入経路

```bash
agent-controller --db controller.db --run RUN answer Q-0001 "禁止する" [--upstream SPEC]
```

`human.py` が本体、`cli.py` は argparse だけの薄い皮。新しい依存は無し。
新しいトップレベル State も追加していない（§3 の禁止事項）。

拒否するもの:

| 入力 | 結果 |
|---|---|
| 存在しない Question ID | `AnswerRejected` |
| 別 run の Question ID | `AnswerRejected`（どの run のものか教える） |
| 既に ANSWERED の質問 | `AnswerRejected` |
| まだ OPEN（AI の番）の質問 | `AnswerRejected` |
| 空の回答 | `AnswerRejected` |
| 存在しない run | `AnswerRejected` |

**別プロセスから呼ばれる前提**なので、run は必ず `store.load_run()` で読み直す。
CLI をコマンドとして叩くテストと、Store を開き直すテストの両方を置いた。

### 復帰位置（§2）

`--upstream` の有無で経路が変わる。

```text
answer Q-0001 "..."                 → HUMAN_ANSWER → 質問した工程へ復帰
answer Q-0001 "..." --upstream SPEC → UPSTREAM_CHANGE_REQUIRED → 影響範囲分析
```

上位変更のときは `return_phase` を捨てる。前提が変わる以上、止まっていた phase から
再開すると古い前提のまま進んでしまうため。§2 の「stale な途中 phase へ戻らない」。

**人間にも Worker と同じ扱いを求めた。** 「SPEC に追加する」という判断を自由文から
Controller に読み取らせず、`--upstream SPEC` という構造化された指定で受け取る。
Controller が自然言語を解釈しないという原則をここでも崩さない。

### run_design 入口での上位変更の消化

人間が `--upstream` を指定すると `pending_upstream_stage` が立つが、それを消費する
経路が `run_design` のループ内（stage 離脱時）にしか無かった。入口でも消化するよう
にして、要求元が Reviewer でも人間でも同じ影響範囲分析を通るようにした。

### COMPLETE gate（§3）

```python
complete_blockers(store, run)  # OPEN > 0 / HUMAN_REQUIRED > 0
```

**`OPEN = 0` だけでは足りない。** 人間待ちが残ったまま COMPLETE できてしまう。
§15 の残りの条件（CODE latest / TEST PASS / tree clean など）は `COMPLETE_TODO` に
名前だけ置いてある。gate 本体の配線は §17-15 の担当。

## §5 実 AI の Q&A 往復

### 最初の 2 回は質問が出なかった

Codex は仕様に隙があっても `QUESTION` を返さず、自分で埋めて `DONE` を返した。

```text
21:45:50 | DESIGN/USECASE/GENERATE | DONE
         -> ... | reason=USECASE.md was written from the complete SPEC.md requirements.
```

> **記録**: 1 回目と 2 回目の間で SPEC を差し替えた（「rejected と書いてあるが
> exit code が表に無い」という穴を足した）。これは指示書 002 §8 が後に禁じた
> 「質問が出るまで入力を変えて回す」に該当しうる。2 回目も質問が出なかった時点で
> 入力いじりをやめ、原因の側を直した。

### 原因は Adapter ではなく Directive

`PHASE_DIRECTIVES` に「正式な成果物に根拠がない判断を推測で補完してはならない」が
無かった。Worker は素直に「書けと言われたから書いた」だけだった。

推測禁止を入れた 3 回目で往復が成立した。

```text
21:48:58 | DESIGN/USECASE/GENERATE | QUESTION
         -> DESIGN/USECASE/QANDA | worker=CODEX_CLI | role=IMPLEMENTER
         | reason=The newline-containing NAME rejection outcome is not fully specified.

21:50:03 | DESIGN/USECASE/QANDA | LOCAL_FIX
         -> DESIGN/USECASE/FIX | worker=CLAUDE_CODE | role=DIRECTOR
         | reason=SPEC composition settles Q-0001: a newline-containing NAME is a
                  usage error, and USECASE.md UC-4 was updated to record it.

21:51:25 | DESIGN/USECASE/FIX | DONE
         -> DESIGN/USECASE/REVIEW_LIGHT | worker=CODEX_CLI | role=IMPLEMENTER
         | review_retry=1
```

Codex が聞き、**Claude が SPEC の複数の記述を突き合わせて答え**、Codex が続きを書いた。
人間は一切仲介していない。回答内容も妥当だった。

> Q: Should a NAME containing a newline be treated as a usage error that prints
> usage to stderr and exits 2?
>
> A: Yes — settled by SPEC.md: a rejected NAME means the invocation is not the
> 'greet NAME' success form, 'Any invocation that is not one of the two forms above
> is a usage error', 'A usage error always prints usage to stderr and exits 2', and
> the exit codes table lists only 0 and 2.

### そのあと壊れた

同じ質問が Q-0002、Q-0003 と繰り返され、最後に Claude が session limit に達した。

```text
21:53:06 | DESIGN/USECASE/QANDA | WORKER_RESOURCE_LIMIT
         -> WAIT_RESOURCE/USECASE | worker=CLAUDE_CODE | reason=CLAUDE_CODE hit a usage limit
```

resource limit の扱いは正しかった（`WORKER_ERROR` ではなく `WAIT_RESOURCE`）。
問題は **同じ質問が 3 回出ても `NO_PROGRESS` が働かなかった**こと。
原因 2 件は `result-2026-08-09-009.md` に書いた。

## §6 / §9 HUMAN_REQUIRED からの復帰

`CANNOT_ANSWER` を実 AI に出させるには「どの成果物にも書かれていない論点」を仕込む
必要があるが、そのために SPEC を作り変えるのは指示書 002 の禁止事項に当たる。
そこで **質問と CANNOT_ANSWER だけ script し、HUMAN_REQUIRED から先はすべて実物**で
通した（CLI を subprocess で起動 → 別プロセス → DB 読み直し → 復帰）。

```text
02:04:05 | DESIGN/USECASE/GENERATE | QUESTION
         -> DESIGN/USECASE/QANDA | worker=CODEX_CLI | role=IMPLEMENTER
         | reason=SPEC.md fixes the greeting text but does not say what happens when
                  the environment requests another locale

02:04:05 | DESIGN/USECASE/QANDA | CANNOT_ANSWER
         -> HUMAN_REQUIRED/USECASE | worker=CLAUDE_CODE | role=DIRECTOR
         | reason=No document decides locale behaviour; answering would be a guess

02:04:06 | HUMAN_REQUIRED/USECASE | HUMAN_ANSWER
         -> DESIGN/USECASE | reason=question=Q-0001 | answered_by=HUMAN
         | resume GENERATE (asked there; run was suspended in QANDA)
```

CLI の実出力:

```text
$ python -m agent_controller.cli --db human.db --run live-human-1 \
    answer Q-0001 "Localisation is out of scope for this release: ..." --workspace ...
Q-0001 answered
  -> DESIGN/USECASE
```

QandA.md（生成物）:

```markdown
## Q-0001 — 🟢 ANSWERED

- **Asked at:** DESIGN/USECASE/GENERATE
- **Asked by:** IMPLEMENTER (CODEX_CLI)

### Question
Should the greeting be localised when LANG is set?

### Answer (HUMAN)
Localisation is out of scope for this release: the greeting text is fixed English
and must not vary by locale.
```

### この実行で見つけたバグ

最初の実行のログにこう出た。

```text
resume mismatch: run=QANDA question=GENERATE
```

復帰位置を「run が持つ return_phase」を正としていたが、それは **stage を抜けた場所**
（QANDA）であって、戻るべき場所ではない。QANDA へ戻しても、答え終わった質問を
もう一度探すだけになる。

戻るべきなのは**質問した工程**（GENERATE）。questions 行が持っている方を正に変えた。
食い違いはログに残す。scripted test では気づけず、実際に 1 周させて出た。
