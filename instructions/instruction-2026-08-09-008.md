# 作業指示 008 — 実AI Phase単体診断と最小完走ルート確立

## 目的

前回の実AI Main Graph E2Eでは、4AI Adapter・Role-aware権限・診断・fallbackは実装済みとなったが、実AI E2Eは `IDLE -> DESIGN -> HUMAN_REQUIRED`、位置 `DESIGN/SPEC` で停止した。

今回の目的は機能追加ではなく、**実AI接続をPhase単位で切り分け、少なくとも1つの実AI構成でMain Graphを `IDLE -> COMPLETE` まで完走できる最小ルートを確立すること**。

4AIを同時に理想配置することを優先しない。まず「どのWorkerなら、どのRole/Phaseを安定して通せるか」を事実として確定し、その事実だけを使って1本の完走ルートを作る。

---

## 絶対条件

既存の `hikitsugi.md` の原則を崩さない。

特に以下を厳守する。

1. Controllerは自然言語の意味を解釈しない。
2. Top-level遷移表とDocumentStage内部遷移表を混ぜない。
3. Top-level Stateは10個のまま増やさない。
4. SQLiteがcanonical state、Markdownはprojection。
5. loop停止はControllerが行い、`recursion_limit`は非常停止のみ。
6. COMPLETEは既存 `CompleteGate` を必ず通す。
7. 実AIを通すためにSQLite、ArtifactStatus、transition、Q&Aを手編集しない。
8. 実AIを通すためにSPECの意味を変えない。
9. 本体Agent-Controller repoを実AI作業workspaceとして使わない。scratch Git workspaceを使う。
10. 失敗を成功扱いにしない。

# 2. SPEC / REVIEW_DEEP を4AIで単体比較する

まず前回停止した `DESIGN/SPEC/REVIEW_DEEP` だけを対象にする。

同一scratch workspace、同一SPEC、同一Directive、同一allowed_eventsを使用し、Workerだけを切り替えて比較する。

候補順は固定してよい。

```text
Claude Code
Codex CLI
Grok
agy
```

ただしcapability上、そのRole/Phaseを許可していないWorkerは「実行失敗」ではなく「capability対象外」として記録する。

各Workerについて最低1回、可能なら同一条件で2回まで確認する。無限再試行しない。

### 合格判定

少なくとも1 Workerが、既存SPECを変更せず、入力文書を読み、正しいstructured resultを返して `PASS` または仕様上妥当な別Eventへ到達すること。

### 失敗時

次のように原因を分類する。

```text
PROCESS_LAUNCH
PERMISSION_OR_TOOLS
PROMPT_TRANSPORT
TIMEOUT
INVALID_OUTPUT
SCHEMA_MISMATCH
RESOURCE_LIMIT
WORKSPACE_ACCESS
OTHER
```

この分類は診断用でありTop-level Eventを増やすために使わない。

# 3. Claude filesystem tools問題を事実確認する

前回の

```text
Filesystem tools (Read/Glob/Bash) are disabled in this session
```

を、Main Graph外の最小Claude Code probeで確認する。

確認対象:

- 現在のClaude CLI version
- 実際に使われたcommand line
- REVIEWER時のpermission/tool指定
- `--tools ""` / `--safe-mode` / `--permission-mode plan` 等、現在Adapterが付与するoption
- 入力artifactをClaude自身が読めるか
- 単なるprompt埋め込みだけでレビュー可能か

### 重要

Claude Codeの実装をOracleCouncilから機械的にコピーしない。

Agent-ControllerのRole契約では、Reviewerはread-onlyでよいが、**read-onlyとfilesystem tool無効は別物**。

Reviewerはファイルを変更してはいけないが、レビュー対象ファイルを読めなければならない。

必要ならClaude Reviewerの権限設定を、

```text
read allowed
write/edit/bash denied
```

という実質的read-only構成に修正する。

CLI optionの意味は、現在インストールされている `claude --help` の実出力を一次資料として確認してから変更する。

推測でoptionを追加しない。

# 4. Codex / Grok / agyも同じ観点で確認する

Reviewer/Director/Answererについて、各Workerが

```text
input artifactを読める
workspaceを書き換えない
structured outputを返せる
```

ことを単体確認する。

特にCodexはread-only sandboxでファイル読取が可能であることを確認する。

Grok/agyがfilesystemを直接読めない設計なら、無理に読ませない。

その場合はControllerが必要なartifact本文をpromptへ与える方式を許容する。ただし以下を守る。

- Controllerは意味を解釈しない。
- 単純に指定artifactの内容を読み込んでWorkerRequestへ添付するだけ。
- promptサイズ上限を超える場合は明示的に失敗する。
- agyのWindows command-line上限guardを維持する。

「Workerがファイルを読む方式」と「Controllerがartifact本文を渡す方式」は、capabilityとして区別する。

# 5. 各主要Phaseを単体で通す

SPEC REVIEW_DEEPが通ったら、Main Graphをまだ回さず、次を順に単体実行する。

```text
DESIGN/USECASE/GENERATE
DESIGN/USECASE/REVIEW_DEEP
DESIGN/SEQUENCE/GENERATE
DESIGN/SEQUENCE/REVIEW_LIGHT
DESIGN/CLASS/GENERATE
DESIGN/CLASS/REVIEW_LIGHT
DESIGN/TESTCASE/GENERATE
DESIGN/TESTCASE/REVIEW_LIGHT
IMPLEMENT/GENERATE
REVIEW/REVIEW_LIGHT
```

UIが必要なSPECでなければUI stageは既存ルールどおりskipしてよい。

各Phaseで「最低1つ成功するWorker」を記録する。

例:

```text
SPEC REVIEW_DEEP       -> Codex
USECASE GENERATE       -> Codex
USECASE REVIEW_DEEP    -> Grok
IMPLEMENT              -> Codex
REVIEW                  -> Codex
```

これは暫定ルーティング表でよい。

# 6. まず1本の最小完走ルートを作る

単体診断で成功実績のあるWorkerだけを使い、Main Graphをscratch workspaceで再実行する。

4AIを必ず全員使う必要はない。

最優先目標は次の1本。

```text
IDLE
-> DESIGN
-> IMPLEMENT
-> TEST
-> REVIEW
-> DOC_SYNC
-> COMPLETE
```

### 推奨

最初は最も安定したWorkerを多くのRoleに使ってよい。

例えば、単体試験でCodexが全工程を通るなら、最初の完走確認は

```text
DESIGN Implementer: Codex
DESIGN Reviewer: Codex
IMPLEMENT: Codex
REVIEW: Codex
```

でもよい。

独立レビュー性はMVP完走後に4AI構成へ戻す。

ただし、同一WorkerをReviewerに使う場合は `quality_mode=SINGLE_AGENT` 等、既存のdegraded状態を正直に記録する。

# 7. Main Graph再実行時の禁止事項

- E2E成功のためにtransitionを手動追加しない。
- FAILをPASSへ書き換えない。
- CompleteGate blockerをDBから削除しない。
- TESTが非0なら自由文でPASS扱いしない。
- REVIEWが落ちたら直接DOC_SYNCへ進めない。
- scratchに前回Workerの半端な変更が残った状態で次Workerを実行しない。checkpoint rollbackを使う。
- HUMAN_REQUIREDになったら、原因が「本当に人間判断が必要」なのか「Worker実行環境の不具合」なのかを診断結果で区別する。

Worker実行環境の不具合を、人間判断が必要な仕様質問と混同しない。

# 8. TEST exit_code=120の扱い

前回のpytest `exit_code=120` は再現性が確定していない。

今回はMain Graph E2E前に、同じscratchで

```text
python -m pytest -q
```

をControllerのtest runnerと同じsubprocess条件で最低3回まで連続実行し、以下を記録する。

```text
raw exit code
signed exit code
elapsed_ms
stdout tail
stderr tail
```

再現しなければ原因を断定しない。

再現する場合だけ、Windows / pipe / timeout / encoding / process termination等を切り分ける。

exit 120を特別扱いでPASSへ変換してはいけない。

# 9. 実AI E2Eが一度COMPLETEした後

一度でも正規経路でCompleteGateを通過した場合のみ、次を行う。

1. 同じscratch入力で再現確認をもう1回行う。
2. 2回目が途中停止しても、最初の成功を消さず再現性を記録する。
3. README / hikitsugi.mdへ以下を明記する。
   - 初めて実AI Main Graph E2EがCOMPLETEしたこと
   - 使用Worker構成
   - quality_mode
   - degraded構成かどうか
   - まだ未確認の4AI構成
4. 次工程として「4AIを使った独立Review/Director構成への拡張」を分離して書く。

COMPLETEしなかった場合はREADMEに完走済みと書かない。

# 10. テスト

通常テストは外部AI非依存を維持する。

```text
uv run pytest -q
```

既存263件を壊さない。

追加すべき主なテスト:

- Phase単体Runnerのrequest組立
- capability対象外Workerを起動しない
- read-only Reviewerが入力artifactを読める構成
- Controllerによるartifact本文添付は内容を解釈せず機械的に渡す
- prompt transport上限
- Worker単体失敗時にworkspace rollback
- fallback後も同じState/Stage/Phase/checkpoint
- HUMAN_REQUIREDとWORKER_ERRORを混同しない
- Main Graphのscripted/fake E2Eを壊していない
- CompleteGate迂回なし

実AI contract testはopt-inのままとする。

# 最終方針

今回の優先順位は次の順。

```text
実AI Phase単体診断
    ↓
SPEC REVIEW_DEEP停止原因確定
    ↓
各Phaseで成功Workerを確定
    ↓
最も安定した1AI/少数AI構成でMain Graph完走
    ↓
その後に4AI独立構成へ拡張
```

今は4AIの美しい役割分担を作る工程ではない。

**まず1本、実AIで正規に `IDLE -> COMPLETE` を通すこと。**
