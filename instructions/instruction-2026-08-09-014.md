# 作業指示 014 — Claude timeout の実原因特定と修正

## 目的

instruction-013 の結果では、Claude Reviewer が 30 秒・120 秒の両設定で semantic result を返さず timeout し、Codex fallback によって Main Graph 自体は COMPLETE まで到達した。

一方、ユーザー側では Claude Code の Usage 画面で現在セッション 0% used、週次 88% used、リセット予定も表示されており、少なくとも「利用枠を使い切っているため動かない」と単純には説明できない。

したがって今回の目的は、**Claude が本当に利用不能なのか、Agent Controller からの起動方法・権限・入出力・実行環境・prompt形式・subprocess制御のどこに問題があるのかを、ログと最小再現で特定して修正すること**である。

「Claude は環境制約で timeout する」と既知制限へ追いやって終了しないこと。

---

## 前提

最新状態:

- Codex 基準 E2E は COMPLETE。
- Claude Reviewer は Main Graph からの起動で 30 秒 / 120 秒 timeout。
- timeout 後の Codex fallback は正常。
- Worker/QANDA の診断 JSONL は既に存在する。
- 通常 pytest は 272 passed, 4 skipped。
- SQLite / Markdown / Git の正本関係、Controller の決定論的制御、10個のトップレベル State は崩さない。

---

## 最重要方針

今回は Claude の timeout を「推測」で説明しない。

最低限、次の3つを区別して証拠を取ること。

```text
A. Claude CLI 自体がこのPCで動かない
B. Claude CLI は手動では動くが Agent Controller 経由だけ止まる
C. Agent Controller 経由でも単純promptは動くが REVIEWER 用 invocation だけ止まる
```

この切り分けを最初に行う。

---

## 1. Claude CLI の基礎動作を同一環境で確認する

Agent Controller を動かしている同じ shell / 同じユーザー / 同じ Python 親プロセス環境から、Claude CLI の最小 probe を行う。

最低限記録するもの:

```text
which / where claude
resolved executable
claude --version
current working directory
shell種類
親process
PATH
PATHEXT（Windowsの場合）
HOME / USERPROFILE
CLAUDE関連env名の一覧（値はsecretなら出さない）
TTYの有無
stdin/stdout/stderrがpipeかterminalか
```

secret/token/cookieの値そのものはログへ残さない。

### 最小probe

まずファイルもtoolも不要な単純promptで確認する。

例:

```text
「JSONで {\"status\":\"ok\"} だけ返して」
```

Agent Controller が使用する実際の subprocess ランナーと可能な限り同じ条件で実行する。

結果として最低限:

```text
start time
first stdout byte time
first stderr byte time
process exit time
exit code
stdout bytes
stderr bytes
```

を測定する。

単に最終 elapsed だけでなく、**最初の出力がいつ発生したか**を記録する。

---

## 2. 「手動成功」と「Controller失敗」の差分を取る

Claude CLI が普通の terminal から動く場合、成功する手動 command と Agent Controller が生成する command を比較する。

比較表を result に残す。

最低限:

```text
executable
arguments
permission mode
allowed tools
output format
session persistence
stdin方式
promptの渡し方
cwd
environment differences
shell=True/False
creation flags
encoding
text/binary mode
stdout/stderr capture
process group
```

特に現在使っている Claude reviewer profile:

```text
--permission-mode plan
--tools Read,Glob,Grep
--no-session-persistence
```

について、各optionを1つずつ減らした最小 probe を行い、どの組み合わせで止まるかを特定する。

ただし大量の総当たりはしない。差分を1変数ずつ変える bounded probe とする。

---

## 3. stdout/stderr を「終了後まとめて」ではなくストリーム監視する

Claude が120秒間完全無反応なのか、stderr等へ何か出しながら待っているのかを確認する。

可能なら診断用 runner で stdout/stderr を非同期またはthreadで逐次読み取りし、次を JSONL へ保存する。

```text
invocation_id
stream
relative_ms
chunk_size
sanitized_tail
```

認証URL、token、secret等は必ずsanitizeする。

特に確認する文字列:

```text
permission
login
auth
browser
trust
workspace
interactive
stdin
tty
mcp
hook
settings
error
warning
```

ただし自由文の単語だけで機械的に resource limit 判定しない。

---

## 4. process tree を確認する

Claude CLI の親子processを観測し、何を待っているのか調べる。

Windows なら可能な範囲で:

```text
python.exe
  -> claude.cmd / node.exe
      -> child process(es)
```

を記録する。

確認事項:

- node process は生存しているか
- CPU時間が増えているか
- stdin read待ちに見えるか
- child processを生成しているか
- timeout時に子processが残留していないか
- terminate後にzombie/残留processがないか

必要なら診断時だけ `psutil` 等を使ってよいが、本番依存に追加する必要がなければ追加しない。

---

## 5. TTY / non-interactive 差を重点確認する

今回の症状では、quota不足よりも「CLIが非対話pipe環境で何かを待っている」可能性を重点的に調べる。

次を比較する。

```text
terminalから直接実行
subprocess + stdin PIPE
promptをargvで渡す
promptをstdinで渡す
shell経由
直接CreateProcess
```

Claude CLI が headless/non-interactive 向けの正式な使い方を要求する場合は、それに合わせる。

既に使っている `-p` / print mode 等があるなら、本当にそのmodeで完全非対話になるか実測する。

---

## 6. Claude 設定・hook・MCPの影響を調べる

Claude Code 側の個人設定により、通常terminalでは問題ないが isolated scratch / non-interactive 実行で止まる可能性を確認する。

最低限:

- Claude settings の読み込み範囲
- project/local/user settings
- hooks
- MCP server
- startup command
- permission rule
- trust / project acceptance

を確認する。

secretはresultへ書かない。

### 重要

もし hook / MCP / startup 処理が原因候補なら、**本番設定を勝手に削除しない**。

診断用の一時設定・明示的無効化option・isolated HOME等で再現性を確認してから、最小修正を決める。

---

## 7. REVIEWER payload の段階的再現

単純promptが動いたら、Main GraphのClaude Reviewer requestへ段階的に近づける。

```text
Step 1: 単純JSON
Step 2: structured Worker JSON schema
Step 3: REVIEWER_RULE追加
Step 4: artifact本文追加
Step 5: 実際のscratch CODE / SPEC context
Step 6: Main Graphと同一prompt
```

各stepで:

```text
prompt chars/bytes
artifact chars
elapsed
first output time
exit
result event
```

を比較する。

どのstepで正常→timeoutへ変化するかを特定する。

---

## 8. timeout時の「入力待ち」を検出する

Claude が hidden prompt / confirmation / permission / trust / login などを要求している可能性を調べる。

stderrだけでなく、可能なら擬似TTYまたは診断用terminal実行で、同一commandを目視できる形でも1回確認する。

ただし人間に操作を要求して止めず、観測結果を記録する。

もし入力待ちが原因なら、正式なnon-interactive optionで回避する。自動で `y` を送る等の力技は禁止。

---

## 9. 原因が分かったら最小修正する

修正候補の例:

- Claude CLIの正しいnon-interactive invocationへ変更
- 不要/矛盾するoptionの削除
- stdinではなくargv / prompt-fileへ変更
- output-formatの扱い修正
- Windows launcher解決修正
- subprocess pipe/deadlock修正
- Claude専用のfirst-output watchdog追加
- hook/MCPをreview worker時だけ明示的に無効化

ただし、**原因が証明できたものだけ修正する**。

「timeoutを120→300秒へ伸ばす」は解決策にしない。

---

## 10. Claude単体Acceptance

修正後、Claude Reviewerだけで最低限次を確認する。

```text
real scratch artifact
-> Claude REVIEWER
-> structured PASS / QUESTION / FAIL のいずれか
-> exit 0
```

PASSを無理に出させなくてよい。

重要なのは **Claude自身が有効なstructured semantic resultを返すこと**。

これを3回連続で実行し、偶然の1回成功でないことを確認する。

3回のelapsedとresultを記録する。

## 11. 2AI Main Graph Acceptanceを再実行する

Claude単体が正常化した場合のみ、新規scratchで同一runの2AI受入を再実行する。

推奨:

```text
IMPLEMENTER = Codex
REVIEWER = Claude
DIRECTOR = Codex
```

または実測で安定したRole routing。

合格条件:

1. 同一runでCodexとClaudeの両方が `WORKER_ERROR` ではない有効なstructured semantic resultを返す。
2. その両方の結果がControllerに採用される。
3. TEST実行。
4. REVIEW結果を機械適用。
5. DOC_SYNC。
6. CompleteGate。
7. `COMPLETE / COMPLETED`。

ClaudeがQUESTION/FAILを返した場合は既存のQ&A/修正loopを自然に回す。

入力を改変してPASSを誘発しない。
