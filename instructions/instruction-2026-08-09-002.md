# Agent Controller 実装指示書 002

## 目的

`instruction-2026-08-09-001.md` の実施中に、実 Worker で重要な挙動が確認された。

- Claude Code は現在の Claude Code セッション内から実起動でき、構造化出力も正常に返せた。
- Codex CLI を実 Worker として使った Q&A E2E では、仕様に曖昧さがあっても `QUESTION` を返さず、自分で補完・推測して処理を進めるケースが確認された。
- これは Worker Adapter の障害ではなく、Directive が「仕様に根拠がない内容を推測してはならない」と十分に拘束していなかったことが原因と考えられる。
- その後 Claude Code の session limit に到達したため、実 AI E2E は途中で停止した。

本指示では、この実測結果を受けて **推測禁止 / QUESTION 必須条件を Worker Directive に正式実装し、resource limit 復帰後に実 AI で Q&A 往復を再実証する。**

新しい大規模機能追加は行わない。既存の State Machine / Worker Interface / QandA / loop guard を使い、今回見つかった制御上の穴を最小変更で塞ぐこと。

---

## 最重要原則

### 1. Worker は仕様に存在しない判断を勝手に補完しない

Implementer / Reviewer / Director など、意味判断を行う Worker に対して、少なくとも次を Directive へ明示すること。

```text
正式な仕様・設計成果物に根拠がない判断を推測で補完してはならない。
後続工程の挙動・設計・テスト結果を左右する不明点がある場合は QUESTION を返すこと。
QUESTION には、何が不明か、どの成果物を確認したか、なぜ既存資料だけでは判断不能かを含めること。
```

Reviewer に対してはさらに、以下を明示すること。

```text
仕様上の根拠が不足している問題を独自解釈で PASS にしてはならない。
根拠不足がレビュー結論へ影響する場合は QUESTION を返すこと。
```

ただし、単なる言い換え・明白な表記揺れ・出力形式上の自明な選択まで無条件に QUESTION にしてはならない。

目的は「質問を増やす」ことではなく、**仕様に存在しない意味判断を Worker が勝手に確定しないこと**である。

---

## 2. Controller は意味を判断しない

「この曖昧さなら質問すべきだった」等を Controller が自然言語解析して判定してはならない。

Controller の責務は従来どおり以下に限定する。

```text
Worker が返した構造化 Event を検証
        ↓
State / Stage / Phase 遷移
        ↓
Q&A 永続化 / Guard / Resume
```

QUESTION を出すかどうかの意味判断は Worker / Director 側に置く。

---

## 3. QUESTION の構造化出力を確認する

既存の WorkerOutput / WorkerResult / StageResult を優先して使い、不要な新モデルを増やさないこと。

QUESTION の場合は、少なくとも次の情報が失われず QandA の questions 行まで届くことを確認する。

```text
Event = QUESTION
question text
reason / context
source role
source worker
source state / substate / phase
return state / substate / phase
related artifact information（既存モデルにある範囲でよい）
```

既存構造で足りない場合のみ最小限追加する。

---

## 実施項目

### 4. Directive の共通制約を実装する

Codex CLI / Claude Code それぞれの Adapter に重複して固定文を書くより、可能なら共通 Directive 生成層へ入れること。

ただし過度な抽象化は避ける。

最低限、DocumentStage の以下の場面へ効くこと。

```text
GENERATE
REVIEW_LIGHT
REVIEW_DEEP
FIX / REWORK（該当する場合）
QANDA / ANSWERER（役割上必要な場合）
```

役割ごとに文面を変える必要がある場合は、共通原則 + role-specific rule 程度に留める。

### 5. scripted test を追加する

通常の `pytest` は外部 AI CLI 非依存を維持すること。

最低限、以下をテストする。

1. Directive に「推測禁止」「根拠が無い場合 QUESTION」の制約が含まれる。
2. Reviewer Directive に「根拠不足を独自解釈で PASS にしない」が含まれる。
3. Worker が QUESTION を返した場合、questions テーブルへ保存される。
4. QUESTION 後の return state / substate / phase が保持される。
5. 既存の WORKER_ERROR 正規化、fingerprint、loop guard を壊していない。
6. 既存テストを変更して通すのではなく、既存挙動との後方互換を保つ。

## 実 AI 実証

### 6. resource limit 中は無理に再実行しない

Claude Code が session limit / resource limit の場合、実 AI E2E を連打しないこと。

State Machine 上で既存の

```text
WORKER_RESOURCE_LIMIT
→ WAIT_RESOURCE
```

相当の扱いを優先する。

CLI が利用可能になった後に §7 以降を実行する。

### 7. Codex → QUESTION → Claude の実 Q&A を 1 周させる

小さい scratch workspace を使用し、リポジトリ本体の正式成果物を実 AI の実証用に書き換えないこと。

テスト用 SPEC は、**既存資料を慎重に読めば Director / Answerer は回答できるが、対象 Worker が現在の入力だけから勝手に決めてはいけない条件**を用意する。

重要：QUESTION を無理に誘発するためだけの不自然な壊れた SPEC にしない。

狙う流れ：

```text
Codex Worker
  ↓ QUESTION
questions table / QandA.md
  ↓
Claude Code Director / Answerer
  ↓ ANSWERED
questions table 更新
  ↓
return state / substate / phase
  ↓
Codex Worker 再開
```

実ログに最低限、次が確認できること。

```text
... | QUESTION
    -> QANDA ...

... | ANSWERED または相当 Event
    -> 元の Stage / Phase ...
```

実装上 Event 名が既存モデルで別名なら、既存設計を優先し、無理に Event を増やさない。

### 8. 「質問が発生しなかった」を成功扱いにしない

今回の目的は Q&A 実接続確認なので、Worker が再び勝手に推測して QUESTION を出さなかった場合は、

```text
E2E_NOT_DEMONSTRATED
```

相当として記録し、原因を分析すること。

単に入力を何度も変えて「たまたま QUESTION が出るまで回す」ことは禁止する。

Directive が実際に Worker へ渡ったか、Worker の構造化出力スキーマが QUESTION を許しているか、プロンプト優先順位に競合がないかを確認する。

## HUMAN_REQUIRED 復帰

### 9. 可能なら同じ実証で HUMAN_REQUIRED → HUMAN_ANSWER も確認する

`instruction-2026-08-09-001.md` で実装対象となっている human answer 入口が既に完成している場合は、追加で次も実証する。

```text
Worker QUESTION
↓
Director / Answerer が既存成果物だけでは回答不能
↓
HUMAN_REQUIRED
↓
人間回答を questions 行へ保存
↓ HUMAN_ANSWER
return_state / return_substate / return_phase
↓
元工程を再開
```

まだ human answer 入口が未完成の場合は、まず `instruction-2026-08-09-001.md` の当該項目を完成させてから実証する。

この指示書のために新しいトップレベル State を追加しないこと。

---

## 10. Guard との整合

Q&A 往復を増やしても、以下を壊さないこと。

- `WORKER_RESOURCE_LIMIT` / `RESOURCE_AVAILABLE` / `HUMAN_ANSWER` は通常の loop retry として数えない。
- 同一質問・同一 finding が繰り返された場合は既存 fingerprint / NO_PROGRESS / LOOP_DETECTED が働く。
- `finding_code` がある場合は構造化 fingerprint を優先し、無い場合の reason fallback も維持する。
- Q&A の回答後に同一 QUESTION が無限再発する場合、人間へ上げられること。

---

## 11. ログ

今回も State Transition Log を最優先で確認する。

人間が次の一連を追えること。

```text
DESIGN/... | QUESTION
           -> QANDA/...

QANDA/...  | ANSWERED
           -> DESIGN/.../元phase
```

HUMAN_REQUIRED の場合：

```text
QANDA/... | HUMAN_REQUIRED
          -> HUMAN_REQUIRED/...

HUMAN_REQUIRED/... | HUMAN_ANSWER
                   -> DESIGN/.../元phase
```

`reason` には人間が読める説明を残す。

制御用 fingerprint と人間向け reason は混同しない。

---

## 12. Claude Code 実接続の扱い

今回すでに、Claude Code が現在の環境から実起動でき、well-formed structured output を返すことが確認されている。

したがって、新しい Adapter を作り直すのではなく、既存 `ClaudeCodeWorker` を利用すること。

もし再実行時に session limit が発生した場合は、それを Adapter 不具合と誤認しない。

以下を区別してログへ残す。

```text
WORKER_RESOURCE_LIMIT
WORKER_ERROR
INVALID_WORKER_OUTPUT
```

既存 Event / エラー型がある場合はそれを使う。

## 禁止事項

- QUESTION を出させるために Controller が自然言語の曖昧さを判断すること。
- Worker が仕様に無い判断を勝手に補完することを前提とすること。
- 実 AI が QUESTION を出すまで入力を無作為に変えて何度も回すこと。
- session limit を WORKER_ERROR と混同すること。
- QandA.md を制御状態の正本へ戻すこと。
- HUMAN_REQUIRED 復帰のためだけに新しいトップレベル State を増やすこと。
- 通常の pytest を外部 AI CLI 必須にすること。
- smoke test のために正式な SPEC.md 等を破壊的に書き換えること。

本作業の主眼は、AI の自主性を弱めることではない。

**AI が判断してよい範囲と、正式仕様へ問い合わせるべき境界を明示し、その境界を State Machine 上の `QUESTION` として観測可能にすること**である。
