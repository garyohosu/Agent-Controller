# 1. 現在確認できている事実

`result-2026-08-09-013.md` の実AI E2Eでは、次まで実際に進んだ。

```text
IDLE → DESIGN → IMPLEMENT → TEST → REVIEW
```

実測:

```text
TEST 1回目 : exit_code=120
TEST 再実行 : exit_code=0, 2 passed
Claude Reviewer : exit_code=4294967295
Codex Reviewer fallback : exit_code=4294967295
最終状態 : HUMAN_REQUIRED
```

このため、現時点では「Claudeが壊れている」「Codexが壊れている」と断定しないこと。

特に **異なる2 CLIが Reviewer 位置で同じ `4294967295` を返した**ため、CLI個別障害だけでなく、共通 subprocess 実行経路、親プロセス側の制限、Windows exit code 表現、外側の実行ハーネスによる終了なども候補に含めて切り分ける。

`4294967295 == 0xFFFFFFFF` であり、32bit signed として見れば `-1` になるが、**数値だけから原因を決めてはいけない**。

# 2. 既存4AI実装から再利用する実測知識

OracleCouncil では Claude / Codex / Grok / agy の4 CLIが実機 live test と4AI E2Eで動作済みである。

少なくとも以下の起動形状は、推測ではなく既存実装の実測結果を参考にすること。

## Claude Code

読み取り専用の評価用途では、OracleCouncil は概ね次の思想で起動している。

```text
claude -p
--tools ""
--output-format json
--no-session-persistence
--safe-mode
prompt は stdin
```

JSON envelope のモデル本文は `result` に入る。

Agent Controller の IMPLEMENTER では書き込み権限が必要だが、**REVIEWER / ANSWERER / DIRECTOR まで `acceptEdits` にする必要はない**。

## Codex CLI

OracleCouncil の読み取り専用評価は概ね次。

```text
codex(.cmd) exec
-s read-only
--ephemeral
--output-schema <temp-schema>
-
prompt は stdin
```

Windows では `codex.cmd` を明示する実装実績がある。
Agent Controller の `resolve_executable()` 方式を残してもよいが、実機でどの実体を起動したかログへ残すこと。

## Grok

既存実績:

```text
grok --prompt-file <temp-file> --output-format json
```

- prompt を argv に直接載せず temp file を使用
- stdout は envelope
- モデル本文は `envelope["text"]`
- temp file は成功/失敗に関係なく削除

## Antigravity / agy

既存実績:

```text
agy --print "<prompt>"
```

- stdout は envelope なしのモデル本文
- Windows では prompt 全体が argv に乗る
- CreateProcess の command line 長制限があるため、実コマンドラインの UTF-16 code unit 数を事前検査する
- 既存 OracleCouncil では安全側の上限を 30000 code units としている

# 3. 最初に障害を切り分ける

製品コードを大きく変更する前に、最小 probe を作ること。

本体成果物を汚さない scratch workspace を使う。

最低限、4 CLI について次を個別に確認する。

```text
1. executable resolve
2. --version / probe
3. 最小の構造化JSON応答 1 回
4. 同じ CommandRunner 経由での実行
```

Main Graph を通さない単独実行と、Main Graph 経由の両方を比較できるようにする。

## 診断として記録する項目

秘密情報や prompt 本文を保存せず、最低限次を記録できるようにする。

```text
worker
role
state / stage / phase
resolved_executable
argv の安全な要約（prompt本文は除外）
raw_exit_code
signed_exit_code
elapsed_ms
timed_out
stdout_length
stderr_length
stdout_tail（必要最小限・redact）
stderr_tail（必要最小限・redact）
```

Windows exit code は、表示用に次の正規化を持ってよい。

```python
signed = raw - 2**32 if raw >= 2**31 else raw
```

ただし **raw値も必ず保存する**。

`4294967295 → -1` と表示できても、それを即 `RESOURCE_LIMIT` や `CANCELLED` と分類してはいけない。

`python -m pytest -q` が Graph 内で一度120、単独では0だった件を放置しない。

# 5. Worker 実行を Role-aware にする

現在の `CliWorker` は Worker種別でコマンドが固定されているが、実際には Role によって必要権限が違う。

少なくとも次を分ける。

```text
IMPLEMENTER
  書き込み可能

REVIEWER / ANSWERER / DIRECTOR
  原則 read-only
```

### 必須条件

- REVIEWER は source を編集しない
- ANSWERER は source を編集しない
- DIRECTOR は意味判断と指示生成だけで、コード編集をしない
- IMPLEMENTER だけが workspace-write / accept edits 相当を使う

Claude / Codex の review profile は、OracleCouncil で実績のある read-only 起動方法を参考にする。

既存の `WorkerRequest.role` を使い、Controller が自然言語から権限を判断する実装にはしない。

# 7. Worker Router / fallback を Controller 配下に入れる

1 Worker を直接 `wired_handlers(reviewer=...)` へ固定するだけではなく、Role に対して適格 Worker の候補列を持てるようにする。

概念:

```text
Role
 ↓
Worker Router
 ↓
eligible workers
 ↓
現在の優先順位で1体選択
 ↓
失敗分類
 ├─ 成功 → 続行
 ├─ RESOURCE_LIMIT → 次Worker または WAIT_RESOURCE
 ├─ WORKER_ERROR → 次Worker
 └─ 全候補失敗 → HUMAN_REQUIRED / WAIT_RESOURCE
```

優先順は設定可能にする。
既存の設計方針（Claude / Codex を優先し、残りを fallback）を初期値としてよい。

### 絶対条件

- State / Stage / Phase は Worker 切替で変えない
- §17-14 の checkpoint から安全に再開する
- 会話コンテキストを Worker 間で引き継がない
- 正本は Git / SQLite / artifacts / Q&A
- resource limit 待ちは loop count に入れない
- 同じ finding が Worker を替えても繰り返された場合は既存 NO_PROGRESS 判定を維持する
- Controller は stderr の意味をAI的に解釈しない。分類規則だけを適用する

**1体目の Reviewer が WORKER_ERROR を返しただけで、まだ適格 Worker が残っているのに HUMAN_REQUIRED へ落とさないこと。**

# 8. CLI error classifier を強化する

現在の `RESOURCE_LIMIT_PATTERNS` は暫定実装なので、OracleCouncil の `classify_cli_error` の設計も比較する。

特に次を確認する。

## 成功stdoutを誤分類しない

モデル回答本文に単に `429` / `quota` / `rate limit` という語が含まれているだけで `WORKER_RESOURCE_LIMIT` にしてはならない。

自由文 fallback を使う場合は原則:

```text
process non-zero
または CLI自身が structured error を返した
```

ときだけに限定する。

OracleCouncil でも「成功出力の本文に quota 等が含まれただけで quota error と誤認する」問題が実機運用で発見され、非zero時だけ自由文 fallback を使うよう修正している。

## 分類と遷移を分ける

可能なら内部 diagnostic code を持つ。

例:

```text
QUOTA_EXCEEDED
RATE_LIMITED
TIMEOUT
COMMAND_NOT_FOUND
INVALID_OUTPUT
PROCESS_NONZERO_EXIT
PROMPT_TOO_LARGE
ABNORMAL_TERMINATION
```

これを既存 Event へ変換する。

```text
quota / rate limit → WORKER_RESOURCE_LIMIT
その他 → WORKER_ERROR
```

トップレベル Event を無闇に増やさない。

# 10. 実AI Main Graph E2E を再実行する

上記を実装・単独probe確認した後でのみ、前回と同等の小さな scratch Git workspace を作って Main Graph E2E を再実行する。

目標経路:

```text
IDLE
→ DESIGN
→ IMPLEMENT
→ TEST
→ REVIEW
→ DOC_SYNC
→ COMPLETE
```

ただし COMPLETE を目的に入力を細工しない。

自然に Worker failure が出た場合は、今回追加した Router が次 Worker へ切り替えることを確認する。

ログ例:

```text
REVIEW | WORKER_ERROR | worker=CLAUDE_CODE | diagnostic=ABNORMAL_TERMINATION
REVIEW | WORKER_SWITCH | from=CLAUDE_CODE | to=CODEX_CLI
REVIEW | WORKER_ERROR | worker=CODEX_CLI | ...
REVIEW | WORKER_SWITCH | from=CODEX_CLI | to=GROK
REVIEW | PASS | worker=GROK
```

既存 Event体系に `WORKER_SWITCH` が無い場合、**ログ専用 action として表現し、トップレベル State Event を増やす必要はない**。

全 Worker が失敗した場合は、その事実を残して安全に停止する。
