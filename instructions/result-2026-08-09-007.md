## 1. 入口の検査 — 指摘は正しく、実際はもっと悪かった

### 何が起きていたか

指摘のとおり SPEC が無検査で通っていた。ただし **smoke run のログはその証拠に
なっていなかった**。あれは `run_design` ではなく USECASE stage 単体を直接叩いた
script なので、SPEC が出てこないのは当然だった。

`run_design` を直接確かめたところ:

```text
ENTER SPEC       at GENERATE
ENTER USECASE    at GENERATE
```

つまり「SPEC レビューが抜けている」というより、**人が書いた SPEC.md を Controller が
上書きし、AI が書き直した文章を DEEP レビューしていた**（review_level=DEEP なので
生成後のレビュー自体は走っていた）。入口の問題という診断はそのとおりで、
直す場所は entry phase のロジックだった。

### 直した後

```text
ENTER SPEC       at REVIEW_DEEP     既存文書は読ませる
ENTER USECASE    at GENERATE        無い文書は作る
```

### 判定の仕方

**新しい状態は 1 つも増やしていない。** 示された意味付けをそのまま使った。

```text
artifact 行なし  → 外部から与えられた既存成果物 → 原則保護（レビューから入る）
artifact 行あり  → Controller 管理下の成果物   → STALE なら再生成
```

`workspace` を渡すと、その工程の出力文書が既に存在するかを見る。
存在すれば `review_level` の強度でレビューから入る（SPEC は DEEP）。
影響範囲分析が `STALE` を書いた工程は、artifact 行があるので文書が残っていても
再生成になる。

`workspace` を渡さなければ従来どおり全工程を生成から始める（既存テストは無変更）。

`FIX_REQUIRED` は `LOCAL_FIX` のまま据え置いた（`REQUEST_CHANGES` のときと同じ）。

## 2. fingerprint の構造化

### 分離

```text
機械判定 → finding_code / finding_subject   （AI が返す）
          + state / substate / phase / event（Controller が知っている）
人間向け → reason
```

`artifact` と `phase` を AI に自己申告させていないのは指摘のとおりの理由による。
Controller が既に知っている事実をもう一度言わせると、不一致を処理する仕事が増える。

### 実測

同じ指摘を 4 通りに言い換える Reviewer に対して:

```text
finding_code あり: 4 回のレビューで停止
finding_code なし: 7 回のレビューで停止
```

対照実験もテストに残してある。code が無くても「いずれ同じ文言を繰り返すので
上限に達する」が、そこまでに無駄な修正を何周も回す。

### 必須にしなかった判断

`finding_code` が無い場合は reason へフォールバックする。

`upstream_target` は制御フローそのものを決める（どこへ戻るか分からないと進めない）
ので必須にしたが、`finding_code` は歯止めの精度を上げるだけなので、
**検出が鈍る方が run が死ぬよりまし**と判断した。厳しくするのは後からできる。

## 3. QandA.md（§17-13）

### 原則

```text
Markdown  意味のある共有成果物（人間と AI が読む）
SQLite    制御状態（正本）
```

`questions` 行が正本で、QandA.md は毎回まるごと生成する。**読み戻さない。**
手で編集しても次の更新で消える（テストで確認している）。
§10 で遷移ログをそうしたのと同じ扱い。

### 一周

```text
Worker
  ↓ QUESTION（question フィールド）
questions 行を作成 → QandA.md 再生成
  ↓
QANDA phase（指示はその質問から組み立てる）
  ├─ DONE          → ANSWERED にして質問元 phase へ復帰
  ├─ LOCAL_FIX     → ANSWERED にしてから FIX へ
  ├─ CANNOT_ANSWER → HUMAN_REQUIRED にして stage を抜ける
  └─ UPSTREAM_CHANGE_REQUIRED → 影響範囲分析へ
```

`LOCAL_FIX` でも回答自体はできているので `ANSWERED` にする。`OPEN` のまま
放置しない。

### migration 機構の初仕事

`questions` テーブルは v2 として追加した。§17-11A で作った枠組みが実際に使われ、
既存 DB を壊さずに列が増えることを確認できた。

### 同じ質問の再発

**専用の検出器は作らなかった。** `QUESTION` は既に指紋を取る Event なので、
質問文を `finding_subject` に載せるだけで既存の `NO_PROGRESS` が数える。
これで §11 の「同一 Q&A の再発検出」も閉じた。

### 出力例

```markdown
# QandA

- Total: 2
- Open: 0
- Waiting on a human: 1

## Q-0001 — 🟢 ANSWERED

- **Asked at:** DESIGN/CLASS/REVIEW_LIGHT
- **Asked by:** REVIEWER (CODEX_CLI)
- **Related:** SEQUENCE.md, SPEC.md, CLASS.md

### Question

Should `greet` be idempotent when called twice with the same name?

### Context

SPEC.md does not mention repeated invocation

### Answer (CLAUDE_CODE)

Yes. SPEC.md says `greet NAME` prints and exits 0, with no state kept, so repeats
are identical.

## Q-0002 — 🟡 HUMAN_REQUIRED

### Question

What exit code applies when NAME is an empty string?

### Answer

_No existing document settles this. A human decision is required._
```

`Open` と `Waiting on a human` を分けて出している。§15 の完了条件は
`QandA OPEN = 0` だが、それを満たしていても人間待ちが残っていることはあるため。

## 未実装事項 / 制約

1. **HUMAN_REQUIRED からの復帰は未実装。** 質問が `HUMAN_REQUIRED` になった後、
   人間が答えて run を再開する経路が無い。`HUMAN_ANSWER` Event と `return_state` は
   あるので、人間の回答を questions 行へ書き戻す入口を作れば繋がる。
2. **実 Worker での QUESTION 往復は未実施。** scripted で一周させただけ。
   Claude Code 実接続と合わせて確かめるのが自然。
3. **Director はまだいない。** QANDA の指示は Controller が質問を貼り付けるだけで、
   「どの成果物を読むべきか」の選択はしていない。
4. **質問は 1 件ずつしか扱わない。** `oldest_open` を回すので、複数同時に開くと
   古いものから順になる。
5. **`related_artifacts` は stage の入出力を丸ごと入れている。** 質問に本当に
   関係するものを選んではいない。
6. 依存グラフは一直線のまま（DAG 化は保留のまま）。
