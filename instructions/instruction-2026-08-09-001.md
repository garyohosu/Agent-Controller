# Agent Controller 実装指示書 2026-08-09-001

## 目的

`instructions/instruction-2026-08-08-001.md` の続きとして、現在までに実装済みの State Machine / DocumentStage / IMPACT_ANALYSIS / loop guard / Worker interface / QandA 基盤を使い、**人間回答からの復帰と実 AI 同士の Q&A 往復を完成させる**。

今回の中心目標は、従来人間が行っていた次の作業を Agent Controller 内で閉じることである。

```text
CLI AI が質問
  ↓
QandA.md / SQLite questions
  ↓
Director / Answerer AI が回答
  ↓
元の Worker / State / Stage / Phase へ復帰
  ↓
必要なら修正
  ↓
Reviewer 再実行
```

AI だけで解決できない場合は `HUMAN_REQUIRED` で停止し、人間が回答した後に同じ run を安全に再開できるようにする。

## 最重要原則

### 1. Controller と AI の責務分離を崩さない

Controller は自由文を意味解釈しない。

```text
AI Worker
  ↓ 構造化結果
Controller
  ↓ 検証
State / Substate / Phase 遷移
```

AI は意味判断を行う。
Controller は Event、return_state、return_stage、return_phase、upstream_target 等の構造化情報を検証して適用する。

### 2. SQLite を制御状態の正本とする

`QandA.md` は表示・共有用の投影であり、制御状態の正本ではない。

人間が `QandA.md` を手編集しても、次回の生成で上書きされてよい。

質問・回答・状態は `questions` テーブルを正本とする。

### 3. トップレベル State を増やさない

今回のために `HUMAN_ANSWER_WAIT` 等の新しいトップレベル State を安易に追加しない。

既存の `HUMAN_REQUIRED`、`DESIGN`、`IMPLEMENT`、`REVIEW` 等と、return 情報を使う。

### 4. 状態遷移ログを最優先で残す

人間が最初に見るのはログである。

「どの State / Stage / Phase で、何が起き、なぜどこへ戻ったか」が一目で分かること。

# 実装内容

## §1. HUMAN_ANSWER の入力経路を作る

現在 `HUMAN_REQUIRED` になった質問から復帰する入口が無いので実装する。

最初は CLI でよい。

概念例：

```text
agent-controller answer Q-0002 "二重呼び出しは禁止とする"
```

CLI 名や具体的な引数形式は既存 CLI 構成に合わせてよい。

最低限、次を行う。

1. Question ID を指定して対象質問を取得
2. 対象が `HUMAN_REQUIRED` であることを確認
3. 人間回答を `questions` テーブルへ保存
4. `answered_by = HUMAN` 相当を保存
5. Question Status を `ANSWERED` にする
6. `QandA.md` を再生成
7. `HUMAN_ANSWER` Event を発生させる
8. 保存済みの return 情報から元の run を再開する

不正な Question ID、既に回答済み、別 run の質問などは安全に拒否する。

---

## §2. HUMAN_REQUIRED からの復帰位置を厳密にする

質問発生時に保存済みの情報を利用し、可能な限り元の作業位置へ戻す。

最低限考慮するもの：

```text
return_state
return_substate / return_stage
return_phase
question_source_state
question_source_stage
question_source_phase
resume_role
```

実装上の名前は既存モデルに合わせる。

重要：

- resource interruption と upstream change を混同しない
- 上位仕様変更を伴う回答の場合は古い phase へそのまま戻らない
- 人間回答によって formal artifact の変更が必要なら、そのまま元 phase へ復帰せず、既存の `UPSTREAM_CHANGE_REQUIRED` / `IMPACT_ANALYSIS` 経路へ送る

---

## §3. COMPLETE gate を Q&A 状態に合わせて確認する

現在の COMPLETE 条件を確認し、最低限次を満たすようにする。

```text
OPEN questions = 0
HUMAN_REQUIRED questions = 0
```

`OPEN = 0` だけでは、人間待ち質問が残ったまま COMPLETE できるため不可。

既存 COMPLETE gate がまだ未実装なら、今回必要な最小限の検証または TODO / test を追加してよい。

---

## §4. Claude Code Worker の実接続を確認する

`ClaudeCodeWorker` Adapter が存在するが、実接続未確認なので確認する。

実行環境上、Claude Code セッションの内側から `claude -p` 等を起動することによる制約がある可能性がある。

以下を確認する。

- 実 subprocess 起動可否
- Windows / shell launcher 差異
- stdout / stderr
- timeout
- non-zero exit
- session limit / rate limit
- JSON / structured output parsing

Codex 接続時に行ったように、外部 Worker の異常出力で Graph を例外終了させないこと。

次のような異常は Controller が扱える Event / WorkerResult へ変換する。

```text
invalid JSON
unknown Event
required field missing
subprocess launch failure
non-zero exit
timeout
session/resource limit
```

制御不能な Worker 出力をそのまま Graph 例外にしない。

---

## §5. 実 AI で QUESTION → ANSWER → 復帰を 1 周させる

scripted Worker ではなく、実 AI を使って Q&A 往復を確認する。

望ましい組み合わせ例：

```text
Codex CLI     = Reviewer / Implementer
Claude Code   = Director / Answerer
```

環境都合で逆でもよい。

最低限、次の一周を実証する。

```text
DESIGN または IMPLEMENT / REVIEW
  ↓
実 Worker が QUESTION
  ↓
questions + QandA.md
  ↓
Director / Answerer 実 Worker
  ↓
ANSWERED
  ↓
元 State / Stage / Phase または適切な修正経路へ復帰
  ↓
処理継続
```

このとき、人間が ChatGPT と CLI AI の間で回答をコピペしてはいけない。

---

## §6. 実 AI で CANNOT_ANSWER → HUMAN_REQUIRED → HUMAN_ANSWER → 復帰を 1 周させる

AI が正式成果物から回答できない質問を意図的に作り、実際に人間待ちへ遷移することを確認する。

```text
Worker QUESTION
  ↓
Director / Answerer
  ↓ CANNOT_ANSWER
HUMAN_REQUIRED
  ↓
人間が answer CLI 等で回答
  ↓ HUMAN_ANSWER
質問 ANSWERED
  ↓
元の適切な処理へ復帰
```

ここでは人間が回答すること自体は正常である。

目的は、人間が **AI 間のメッセンジャーをすることではなく、本当に仕様判断が必要な時だけ回答する** 形を確認すること。

---

## §7. 人間回答による上位仕様変更を 1 ケース確認する

可能であれば、人間回答が単なる局所回答ではなく、上位成果物変更を必要とするケースもテストする。

例：

```text
Question:
「同一名前の登録を許可するか？」

Human Answer:
「禁止する。SPEC に正式に追加する」
```

この場合、単純に元 phase へ戻さず、既存の影響範囲分析へ接続する。

```text
HUMAN_ANSWER
  ↓
SPEC_CHANGE_REQUIRED / UPSTREAM_CHANGE_REQUIRED
  ↓
IMPACT_ANALYSIS
  ↓
必要な Artifact だけ STALE / REVIEW_REQUIRED
  ↓
再設計
```

実装負荷が大きい場合は、まず scripted test で経路を確認し、実 AI E2E は後続にしてよい。その場合は result に明記する。

## §8. Q&A loop と loop guard の統合確認

Q&A が入ったことで loop guard が壊れていないことを確認する。

特に：

- `HUMAN_REQUIRED` で待っている時間や `HUMAN_ANSWER` は無限ループ回数として数えない
- 同じ質問が繰り返される場合は既存の Q&A 再発検出 / fingerprint が効く
- finding_code がある場合は構造化 fingerprint を優先
- finding_code が無い場合の reason fallback は維持してよい
- Worker を切り替えても同一失敗が続く場合の `NO_PROGRESS` が壊れていない

## §9. 状態遷移ログ

今回追加する経路について、最低限次のようなログが読めること。

例：

```text
06:10:01 | DESIGN/CLASS/REVIEW_LIGHT | QUESTION
         -> ANSWER_QUESTION/CLASS | worker=CODEX_CLI | question=Q-0003

06:10:15 | ANSWER_QUESTION/CLASS | CANNOT_ANSWER
         -> HUMAN_REQUIRED/CLASS | worker=CLAUDE_CODE | question=Q-0003
         | reason=no existing artifact defines duplicate-name behavior

06:15:02 | HUMAN_REQUIRED/CLASS | HUMAN_ANSWER
         -> DESIGN/CLASS/FIX | question=Q-0003
         | answered_by=HUMAN
```

上位変更の場合：

```text
06:15:02 | HUMAN_REQUIRED/CLASS | HUMAN_ANSWER
         -> IMPACT_ANALYSIS | question=Q-0003
         | reason=SPEC change required
```

実際の State 名・表示形式は既存実装に合わせる。

## §10. テスト

既存テストを壊さない。

最低限追加すること：

1. HUMAN_REQUIRED question へ人間回答を書き戻せる
2. 回答済み質問への二重回答を拒否
3. 不正 Question ID を拒否
4. `QandA.md` が DB 状態から再生成される
5. `HUMAN_ANSWER` 後に return 位置へ復帰する
6. 上位変更が必要な回答では stale な途中 phase へ戻らない
7. `OPEN=0` でも `HUMAN_REQUIRED>0` なら COMPLETE 不可
8. Claude Worker parser / error translation
9. 実 Worker QUESTION の structured result を Controller が検証できる
10. Q&A 往復が loop guard の誤検出を起こさない

可能なら実 AI smoke test は通常の単体テストとは分離し、通常 `pytest` がネットワーク / AI CLI 非依存で完走する構成を維持する。
