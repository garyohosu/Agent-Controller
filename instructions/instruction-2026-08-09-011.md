# 作業指示 011 — 実AI REVIEW/Q&A 120秒timeoutの原因特定と再現性のある診断

## 目的

`instructions/result-2026-08-09-017.md` では、監査後の実AI Main Graph E2Eが

```text
IDLE → DESIGN → IMPLEMENT → TEST → REVIEW
```

まで進み、TESTはPASSしたが、REVIEWでCodexがQUESTIONを生成した後、Q&A処理中に120秒でtimeoutした。

Q&Aの質問自体はSQLiteにOPENとして残っており、COMPLETEへの強制遷移も行われていない。したがって、今回は新機能追加ではなく、**どの処理が120秒を消費したのかを観測可能にし、最小再現で原因を特定すること**を最優先とする。

「たぶんCodexが遅かった」で終わらせないこと。ログ、時刻、promptサイズ、CLI実行時間、Q&A内部ステップを記録し、どこで止まったのかを証拠で示す。

---

## 前提

最新の `result-2026-08-09-017.md` を前提とする。

確認済み:

- Main Graph正常系は過去にCodex-onlyでCOMPLETE実績あり。
- 監査後コードでは REVIEW FAIL → IMPLEMENT修正ループ等のFake/Scripted統合テストは通過。
- 今回は REVIEWでQUESTIONが生成され、SQLiteへOPEN保存された。
- その後、120秒の実行時間内に実AI側の回答が返らずE2Eが停止した。
- 通常pytestは外部AI/network非依存を維持する。

---

## 最重要方針

### 1. いきなりE2E全体を何度も回さない

まず前回のscratch証跡とSQLiteを読み、最後に成功したtransitionと最後に開始した外部AI呼び出しを特定する。

次に、問題の1工程だけを切り出して再実行する。

### 2. timeoutを伸ばすだけで終わらせない

300秒等へ一時的に伸ばす診断は許可するが、それは原因切り分けのために使う。

単純にtimeoutを延長して「通ったので解決」としてはならない。

### 3. 原因を推測で決めない

最低限、次の候補を証拠で切り分ける。

```text
A. Codex CLIそのものの一時的な遅延
B. Q&A prompt/contextが大きすぎる
C. 同一Worker連続利用による遅延またはCLI状態問題
D. Controller内部で外部AI呼び出し前後に時間を消費している
E. 外側E2E runnerの120秒上限がCLI Worker timeoutより短い
F. Q&Aが意図せず複数回Workerを呼んでいる
G. WorkerRouter/fallbackが直列に複数AIを試し、合計で120秒を超えている
H. subprocessが終了しているのにstdout/stderr回収・parse・Git処理等で止まっている
I. 同じOPEN questionが再処理されるループに入っている
```

## 1. 前回E2Eの証跡を復元する

前回scratch workspace / SQLiteが残っている場合、まずそれを解析する。

最低限、時系列で以下を出す。

```text
run_id
transition timestamp
state/substate/phase
event
role
worker
question_id
checkpoint SHA
Worker invocation start/end
elapsed_ms
raw/signed exit code
timeout flag
prompt size
input artifact count / total chars
stdout bytes
stderr bytes
```

既存DBに値が無ければ、無いことを明記し、今回の診断実装で追加する。

「最後のSQLite transition」と「最後のCLI開始ログ」の時刻差から、どこで止まったかを最初に絞る。

---

## 2. Worker呼び出しの構造化診断ログを追加する

既存の `CommandResult` / `WorkerResult.diagnostic` を拡張し、外部AI呼び出しごとに次を必ず記録できるようにする。

```json
{
  "invocation_id": "...",
  "run_id": "...",
  "state": "REVIEW",
  "substate": null,
  "phase": "QANDA",
  "role": "DIRECTOR",
  "worker": "CODEX_CLI",
  "started_at": "...",
  "finished_at": "...",
  "elapsed_ms": 12345,
  "timeout_seconds": 180,
  "resolved_executable": "...",
  "raw_exit_code": 0,
  "signed_exit_code": 0,
  "timed_out": false,
  "prompt_chars": 12345,
  "prompt_utf8_bytes": 23456,
  "artifact_chars": 10000,
  "question_chars": 250,
  "stdout_chars": 500,
  "stderr_chars": 0,
  "result_event": "PASS"
}
```

注意:

- prompt本文そのものを通常ログへ丸ごと保存しない。
- 秘密情報やartifact本文を診断ログへ複製しない。
- サイズ、hash、件数、末尾の安全な短縮情報を中心とする。
- raw outputが既存設計上保存される場合も、公開ログではtail長を制限する。

SQLite canonicalに入れるか、scratch診断JSONLとして残すかは既存設計と整合する最小変更でよい。ただしresultから時系列を再構築できること。

## 3. Main Graph / QANDA内部のstep timingを追加する

外部AIだけでなく、Controller内部の主要処理にもmonotonic clockで所要時間を計測する。

最低限:

```text
REVIEW worker execute
QUESTION SQLite save
QANDA load question
Director request build
artifact content collect
prompt build
WorkerRouter candidate 1
WorkerRouter candidate 2 ...
result parse / schema validate
QANDA status update
Git checkpoint / rollback / commit
transition record
```

目的は、120秒の大半をどこが使ったかを見えるようにすること。

通常動作のログを過度に増やさない。`--diagnostic`、環境変数、またはscratch実行時だけ有効化できる設計を優先する。

## 4. Q&A 1件だけの最小再現Harnessを作る

前回OPENになった質問、または同等の保存済み `WorkerRequest` を使って、Main Graph全体を通さず次だけ実行できる診断Harnessを用意する。

```text
saved question
+ 同じ正式artifact本文
+ 同じDirector directive
→ Worker 1回
→ structured result
```

最低限Codexで3回実行し、それぞれ

```text
elapsed_ms
prompt size
exit code
result event
```

を比較する。

入力を都合よく短く書き換えない。まず前回条件を再現する。

## 5. 4AIで同一Q&Aを比較する

同じQ&A requestを、可能な範囲で以下へ1回ずつ渡す。

```text
Codex
Claude
Grok
agy（capability/permission上可能な場合のみ）
```

比較表をresultへ記録する。

例:

```text
Worker   elapsed   event/error   prompt chars   exit
Codex     145s     PASS          18,400         0
Claude     22s     PASS          18,400         0
Grok       95s     PASS          18,400         0
agy        N/A     permission     ...           ...
```

ここから、Worker固有かprompt共通かを切り分ける。

同時並列実行は避け、quotaやCPU負荷が比較を汚さないよう逐次でよい。

## 6. promptサイズと内容構成を監査する

Q&A requestに何が入っているかを項目別に計測する。

```text
base directive chars
NO_GUESSING_RULE chars
REVIEWER/DIRECTOR rule chars
question chars
artifact A chars
artifact B chars
transition/history chars
previous finding chars
schema chars
その他
```

もし同一artifactが重複添付されている、不要な全文が複数回入っている、過去ログを無制限に積んでいる等があれば修正する。

ただし、必要な根拠を削ってAIに推測させるような「高速化」は禁止。

削減する場合は、Controllerが意味要約しないこと。重複除去、明らかな機械的メタデータ削減、対象artifact選択の既存ルール改善など決定論的な方法を使う。

---

## 7. timeoutの階層を明確化する

現在のtimeoutを一覧化する。

```text
外側shell / command timeout
Main Graph実行harness timeout
CliWorker timeout
各Adapter timeout
subprocess timeout
LangGraph recursion_limit
```

今回の「120秒」がどの層の120秒だったかを確定する。

外側runnerが120秒、CliWorkerが900秒など不整合があるなら、外側が先に殺して診断情報を残せない構造になるため修正する。

原則:

```text
外側診断harness timeout > Worker timeout + cleanup余裕
```

とし、Controller自身がtimeoutを観測して `WORKER_ERROR` / `WORKER_RESOURCE_LIMIT` 等へ正しく変換できるようにする。

ただし本番timeout値の恒久変更は、実測結果を根拠に決める。

---

## 8. Q&Aの多重呼び出し/ループを確認する

同じ `question_id` について

```text
Director invocation count
WorkerRouter candidate count
QANDA entry count
transition count
```

を確認する。

同じquestionを1回処理するつもりで複数回Workerへ投げていないか確認する。

同一OPEN questionの再入場が起きる場合は、既存fingerprint/guardと整合する形で修正する。

## 9. 原因が判明したら最小修正する

原因別の修正例:

### 外側120秒が原因

- harness timeoutをWorker timeoutより長くする。
- Ctrl+C/killではなくControllerにtimeout処理させる。

### prompt重複が原因

- 機械的重複を除去。
- artifactの同一本文を二重添付しない。

### Codexだけ遅い

- Q&A/Director roleはClaude/Grokを先にする等、既存WorkerRouterのrole priorityを実測に基づき変更。
- Codexをfallbackへ下げてもよい。

### WorkerRouter直列合計が原因

- 各candidateのtimeout policyを明示。
- 1候補がtimeoutした後に残り時間0のまま次候補へ行かない。

### Controller内部処理が原因

- その処理を最小修正し、テストを追加。

原因を確定できない場合は、推測修正を複数入れない。

## 10. 再検証

修正後は順番を守る。

1. 通常pytest全件
2. Q&A最小Harness
3. REVIEW→QUESTION→QANDAだけの統合テスト
4. 新規scratchで実AI Main Graph E2E

E2Eでは診断ログを有効化する。

目標:

```text
IDLE
→ DESIGN
→ IMPLEMENT
→ TEST
→ REVIEW
→ QUESTION（自然発生した場合）
→ QANDA/Director
→ 復帰
→ REVIEW
→ DOC_SYNC
→ COMPLETE
```

自然にQUESTIONが発生しなければ、それを成功条件にするため入力を書き換えない。正常系COMPLETEと、保存済みQ&A最小Harnessの両方を証拠とする。

## 禁止事項

- 120秒を300秒に変えただけで「解決」とする。
- 質問文を短く改変して再現成功を演出する。
- SQLiteのOPEN questionを手動削除して進める。
- CompleteGateを迂回する。
- timeoutをRESOURCE_LIMITと決めつける。
- `reason`自由文だけから原因分類する。
- 通常pytestから外部AIを呼ぶ。
- 1回速かっただけで原因確定する。
