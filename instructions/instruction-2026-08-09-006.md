# Agent Controller 作業指示書 006

## 対象

前工程 `instructions/result-2026-08-09-012.md` で Main Graph の実配線が完了した。

現在は scripted / fake Worker による E2E で、以下が通ることまで確認済みである。

```text
IDLE
→ DESIGN
→ IMPLEMENT
→ TEST
→ REVIEW
→ DOC_SYNC
→ COMPLETE
```

今回の目的は、新機能を増やすことではない。

**現在の Main Graph を実 AI Worker で最後まで 1 周させ、MVP の実機 E2E を確認すること。**

---

## 最重要方針

### 1. 既存設計を崩さない

`hikitsugi.md` の「絶対に崩してはいけない 5 つ」を厳守する。

特に以下を変更しないこと。

```text
- Controller は自然言語の意味を解釈しない
- トップレベル State は 10 個のまま
- TRANSITIONS と STAGE_TRANSITIONS を混ぜない
- SQLite が制御状態の正本
- Loop Guard は Controller が機械的に行う
```

実 AI E2E を通すためだけの例外分岐・特別扱い・ハードコードを入れてはならない。

---

### 2. 正式リポジトリを smoke test の作業対象にしない

実 AI の E2E は必ず **scratch workspace** で行うこと。

Agent-Controller 本体の正式な `SPEC.md`、README、設計成果物、ソースコードを E2E の Worker に変更させてはならない。

推奨構成例：

```text
scratchpad/live-e2e-001/
  SPEC.md
  README.md
  src/
  tests/
```

scratch workspace 自体は Git repository とし、必要なら local bare repository を upstream として使う。

§17-14 の checkpoint / rollback / push 判定を実際に通せる形にすること。

テスト用 workspace が本体 repo の tracked file を変更しないことを実行前後で確認する。

## E2E 用タスク

小さく、AI が数分で実装可能で、テスト結果を機械判定できる課題を使う。

例：Python の小さな CLI。

```text
コマンド:
  greet NAME

要件:
- stdout に `Hello, NAME!` を 1 行出力する
- NAME が空なら終了コード 2
- pytest で正常系・異常系を確認できる
```

これは例であり、既に scratch 用の適切な SPEC があれば再利用してよい。

ただし、特定の Event を発生させるために不自然な矛盾・罠を仕込まないこと。

今回の第一目的は **自然な正常系 E2E の完走** である。

---

## Worker 構成

実行可能な AI CLI を実際に使う。

初期構成は以下を基本とする。

```text
DESIGN Implementer : Codex CLI
DESIGN Reviewer    : Claude Code または Codex CLI
IMPLEMENT          : Codex CLI
REVIEW             : 可能なら Claude Code
```

ただし session / quota 状況に応じて既存 Worker routing を使用する。

Claude Code が利用不能なら、Codex CLI 単独の degraded mode を許容する。

その場合は結果書に必ず以下を記録する。

```text
quality_mode = SINGLE_AGENT
reason = Claude unavailable / resource limit / etc.
```

Worker 切替のために Controller の意味判断を追加してはならない。

## 実施内容

### 1. 事前確認

以下を確認する。

```text
git status --short
HEAD == origin/main
uv run pytest -q
Codex CLI executable
Claude Code executable（利用可能なら）
```

通常 pytest はこれまでどおり外部 AI CLI 非依存であること。

---

### 2. scratch Git workspace を作る

実 AI E2E 専用 workspace を作る。

最低限：

```text
- SPEC.md
- README.md
- Python project / test skeleton
- Git repository
- clean working tree
- upstream が必要なら local bare repository
```

初期 commit を作成し、checkpoint の基準 SHA が明確な状態から開始する。

---

### 3. Main Graph を実 Worker で起動する

stage を直接呼ぶ smoke test ではなく、**Main Graph の入口から起動すること。**

期待するトップレベル経路：

```text
IDLE
→ DESIGN
→ IMPLEMENT
→ TEST
→ REVIEW
→ DOC_SYNC
→ COMPLETE
```

DESIGN 内部では既存の Progressive Refinement を実際に使用する。

```text
SPEC
→ USECASE
→ SEQUENCE
→ CLASS
→ UI（必要な場合）
→ TESTCASE
```

既存 SPEC は上書きせず、レビューから開始する現在の仕様を維持すること。

---

### 4. 状態遷移ログを保存する

実行後、Main Graph の全体が読めるログを result に載せる。

最低限、以下が確認できること。

```text
IDLE -> DESIGN
DESIGN -> IMPLEMENT
IMPLEMENT -> TEST
TEST -> REVIEW
REVIEW -> DOC_SYNC
DOC_SYNC -> COMPLETE
```

DESIGN 内の代表的な DocumentStage 遷移も数行載せる。

DocumentStage の PASS が直接 IMPLEMENT に飛んでいないことを確認する。

---

### 5. 実 AI の成果物を確認する

最低限確認する。

```text
- SPEC を勝手に書き換えていない
- USECASE / SEQUENCE / CLASS / TESTCASE が生成またはレビューされている
- IMPLEMENT が実コードを変更した
- TEST が本当に test command を実行した
- REVIEW が Worker の構造化結果を受けた
- README が LATEST または NOT_REQUIRED になった
```

AI の自由文を Controller の判定根拠に使わないこと。

---

### 6. CompleteGate の実機確認

実 AI E2E でも COMPLETE の直前に既存 `CompleteGate` を必ず通す。

以下の成立を確認する。

```text
設計成果物 VALID
CODE latest
TEST PASS
REVIEW PASS
QandA OPEN = 0
QandA HUMAN_REQUIRED = 0
README latest / NOT_REQUIRED
Git clean / committed / pushed
```

最終的に、

```text
Complete: YES
```

となること。

## 自然に異常系が発生した場合

異常系を意図的に作らなくてよい。

ただし実行中に自然に以下が起きた場合は、その挙動を実測として記録する。

```text
QUESTION
WORKER_RESOURCE_LIMIT
WORKER_ERROR
LOCAL_FIX
UPSTREAM_CHANGE_REQUIRED
HUMAN_REQUIRED
```

### QUESTION が自然発生した場合

既存 Q&A ループをそのまま使う。

```text
Worker
→ QUESTION
→ questions table / QandA.md
→ Answerer / Director
→ ANSWERED
→ 質問した元 phase へ復帰
```

期待する Event を出させるために SPEC を書き換えたり、入力を何度も調整したりしないこと。

### WORKER_RESOURCE_LIMIT が起きた場合

失敗扱いで無理に再実行しない。

```text
WORKER_RESOURCE_LIMIT
→ rollback
→ Worker fallback または WAIT_RESOURCE
```

既存 §17-14 の経路を使う。

session limit を `WORKER_ERROR` に混ぜない。

### HUMAN_REQUIRED になった場合

無理に AI に回答させない。

正式成果物に根拠がない質問なら、そこで E2E を停止してよい。

その場合は「正常完走できなかった」ことを結果書へ正直に記録し、どの質問で停止したかを残す。

---

## 禁止事項

以下は禁止。

```text
- COMPLETE に到達させるために SQLite を手編集する
- ArtifactStatus をテストコードから強制 VALID にする
- TEST PASS / REVIEW PASS を手動挿入する
- Worker の出力を人間が書き換えて Graph に戻す
- AI が期待 Event を返すまで入力を変えて再試行する
- 本体 repo の正式成果物を smoke test で変更する
- recursion_limit を通常の loop 制御として使う
- Controller に自然言語判断を追加する
```

実 AI E2E で穴が見つかった場合は、穴を隠さず原因を特定する。

必要なコード修正は行ってよいが、なぜ scripted test では見つからなかったかを result に書くこと。

---

## テスト

コード修正が発生した場合は対応する deterministic test を追加する。

最後に必ず：

```text
uv run pytest -q
```

通常の test suite は外部 AI / network に依存させない。

実 AI E2E は通常 pytest とは分離すること。

## README / hikitsugi

実 AI E2E の結果を反映する。

成功した場合は、README / `hikitsugi.md` の記述を、

```text
scripted E2E のみ
```

から、

```text
Main Graph を実 AI で IDLE → COMPLETE まで実証済み
```

へ更新する。

ただし、実際に COMPLETE まで到達した場合のみ書くこと。

途中停止なら、到達した State と停止理由を書く。

## 完了条件

以下を全て満たしたら本指示を完了とする。

```text
1. scratch Git workspace で実行した
2. Main Graph の入口から実 AI を起動した
3. DESIGN / IMPLEMENT / TEST / REVIEW / DOC_SYNC を実際に通した
4. CompleteGate を迂回していない
5. 実 AI で COMPLETE まで到達した、または停止理由を正確に記録した
6. 状態遷移ログを結果書に残した
7. 通常 pytest が全件 PASS
8. README / hikitsugi を事実に合わせて更新した
9. result ファイルを作成した
10. commit + push 済み
11. HEAD == origin/main
12. git status --short が空
```
