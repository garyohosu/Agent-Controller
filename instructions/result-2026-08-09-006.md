## §17-11A DB migration

実 Worker を繋ぐと DB は本物の運用データになる。schema を変えるたびに作り直して
いては「途中から再開できる」という性質そのものが壊れるので、実接続の前に片付けた。

- 適用済みバージョンを **1 行ずつ追記**する。更新ではないので、
  「いつどれを当てたか」がそのまま履歴になる
- **v1 は現在の schema をそのまま基準**とする。v1 以前の DB は存在しないので、
  002〜005 の変更を人工的な履歴として再構成することはしない
- バージョン管理前の DB（テーブルはあるが `schema_version` が無い）は、形を推測して
  ALTER せず拒否する。コードより新しい DB も拒否する（古いコードで壊さない）
- `Store(path)` の呼び出し方は変えていないので既存 150 テストは無変更

### テストが見つけたバグ

「途中で失敗したマイグレーションは巻き戻る」というテストが落ちた。

python の `sqlite3` は **DML でしか暗黙のトランザクションを張らない**ため、
`with conn:` で囲っても DDL（`ALTER TABLE`）は即コミットされ、
バージョン行だけ巻き戻って列だけ残る。`BEGIN` / `COMMIT` を明示して直した。
SQLite 自体は DDL もトランザクションに含められる。

> **これで results 002〜005 に毎回書いていた「マイグレーション経路が無い」という
> 積み残しは解消した。**

## §17-11B Worker Interface

指示どおり薄くした。この層は「何を頼み、何が返るか」の形だけを決める。

```python
WorkerRequest   role / state / stage / phase / workspace / input_artifacts /
                output_artifact / directive / expected_output_schema / allowed_events
WorkerResult    event / structured_result / reason / files_changed / raw_output
WorkerAdapter   run(request) -> result
```

- `input_artifacts` は**パスの列挙**にした。中身は Worker 自身に読ませる。
  Controller がファイルを読んで渡す形にすると、Controller が厚くなるうえ、
  「この工程に必要なものだけ渡す」（memo.md §4.2）という意図はパスの列挙で足りる
- `phase_handlers_from_worker` は `Role -> Adapter` の dict を受けるので、
  Implementer と Reviewer を別 Worker にできる（指示書 §13）。1 つだけ渡せば単独運転
- phase ごとの Role は `GENERATE`/`FIX` → IMPLEMENTER、`REVIEW_*` → REVIEWER、
  `QANDA` → DIRECTOR（memo.md §5）

### 命名の逸脱（要確認）

示された `class Worker` は使えなかった。`models.Worker` が既に enum で、
全テーブルとテストに入っているため。基底側を **`WorkerAdapter`** とし、
具象クラスは示された図どおり `ClaudeCodeWorker` / `CodexCliWorker` とした。

## §17-11C Adapter と「Worker 出力を信用しない」

### 実接続の前に塞いだ穴

これまでの scripted stub は書いた本人が形を保証していたので、
`MissingUpstreamTargetError` のような例外を投げてよかった。
**subprocess の出力にはその保証が無い。**

実 AI が `UPSTREAM_CHANGE_REQUIRED` を `upstream_target` 無しで返すと、
graph の node の中で例外になり、遷移も記録されず `HUMAN_REQUIRED` にもならないまま
run が落ちる。これは実接続の前に必ず塞ぐ必要があった。

現在は以下がすべて `WORKER_ERROR` に翻訳され、生の出力を添えて遷移として記録される。

| 壊れ方 | 扱い |
|---|---|
| JSON が無い / 壊れている | `WORKER_ERROR` |
| 知らない Event 名 | `WORKER_ERROR` |
| `upstream_target` 無しの `UPSTREAM_CHANGE_REQUIRED` | `WORKER_ERROR` |
| `upstream_target` が工程名でない | `WORKER_ERROR` |
| その phase で許されない Event（GENERATE が PASS を返す等） | `WORKER_ERROR` |
| 非零終了 / timeout / CLI が起動できない | `WORKER_ERROR` |
| 出力に利用制限らしき文字列 | `WORKER_RESOURCE_LIMIT` |

利用制限の判定は文字列一致の当て推量（`rate limit`, `429`, `usage limit` 等）。
外したら「本当は待てばよかったのに人間を呼ぶ」だけなので安全側に倒れる。

### CLI の起動

`codex exec --help` / `claude --help` の実出力から起こした（記憶で書かない）。

```text
codex  exec --cd <workspace> --skip-git-repo-check --sandbox workspace-write
            --output-last-message <file>          プロンプトは stdin
claude -p --output-format json --permission-mode acceptEdits --add-dir <workspace>
```

`codex` は最終メッセージだけを別ファイルに書かせるので、進捗ログと混ざらない。
`claude` は JSON 封筒を返すので `result` を取り出してから JSON を探す。

JSON 抽出は「フェンス付きブロック → 最後の `{...}`」の順。AI は指示しても
前後に文章を付けるので、素直に `json.loads` できる前提は置いていない。

## 実接続で見つかったバグ

**最初の smoke run は失敗した。**

```text
21:04:21 | DESIGN/USECASE/GENERATE | WORKER_ERROR
         -> HUMAN_REQUIRED/USECASE | worker=CODEX_CLI | role=IMPLEMENTER | reason=CODEX_CLI exited with -1
```

Windows では npm 由来の CLI が `codex`（sh スクリプト）と `codex.cmd`（ランチャ）の
両方で置かれる。`CreateProcess` は `PATHEXT` を見ないので、素の名前のままでは
起動できなかった。`shutil.which` で解決するようにして直した。

**注目すべきは、この失敗が例外ではなく遷移ログに残っていたこと。**
「Worker 出力を信用しない」方針が、最初の実接続でそのまま効いた。
人間が見るのは 1 行のログで、そこに理由が書いてある。
