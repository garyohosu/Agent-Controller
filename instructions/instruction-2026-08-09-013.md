# 作業指示 013 — 最後まで止めずに回す自律修正・受入ループ

## 目的

`instructions/result-2026-08-09-019.md` を前提に、残っている受入未達を1件ずつ人間へ返さず、**原因調査 → 最小修正 → テスト → 実AI再実行**を自律的に繰り返し、MVP受入条件を満たすところまで一気に進める。

前回はCodex基準E2EはCOMPLETE済みだが、同一runの2AI受入で以下が残った。

```text
Codex IMPLEMENTER: DONE
Claude REVIEWER: timeout
Codex REVIEWER fallback: QUESTION
Codex DIRECTOR: DONE
同じReview QUESTIONが再発
→ 収束せず、外側Harness上限で停止
```

今回の最重要目標は次の2点。

1. **Q&A回答後に同一Review QUESTIONが再発するループを収束させる。**
2. **同一run内で2種類以上の実AIを実際に呼び、最終的にCOMPLETEまで到達する。**

途中でバグや失敗を見つけても、その都度作業終了しない。安全に自動修正可能な範囲は自律的に修正して再実行する。

## 最終到達条件

以下をすべて満たすまで、boundedな自律ループを継続すること。

1. 通常pytestが全PASSする。
2. Codex基準Main Graph E2EがCOMPLETEする。
3. 同一run内で2種類以上の実AI invocationが実際に存在する。
4. その2AI runが `IDLE → ... → COMPLETE` まで到達する。
5. Worker fallbackが発生した場合、State / Stage / Phase / checkpoint / Q&A復帰位置を失わない。
6. REVIEW QUESTION → Director/Q&A → 回答反映 → REVIEW再実行が収束する。
7. CompleteGateを迂回しない。
8. SQLite / ArtifactStatus / QandAを手編集して成功を作らない。
9. Git clean / commit / push / `HEAD == origin/main` を確認する。

最終判定は次のいずれかだけを使う。

```text
MVP_ACCEPTED
MVP_ACCEPTED_WITH_KNOWN_LIMITATIONS
RESULT_PRODUCED_WITH_LIMITATIONS
```

`MVP_ACCEPTED` は上記1〜9をすべて満たした場合のみ使用する。

## 1. まずQ&A再質問ループを再現・解析する

前回scratchまたは同等の新規scratchで、次の自然経路を再現する。

```text
REVIEW
→ QUESTION
→ QANDA / DIRECTOR
→ ANSWER
→ REVIEW再実行
→ 同一QUESTION再発
```

診断JSONLとSQLite transition/question履歴を使って、同じ質問が再発する直前・直後の状態を比較する。

最低限記録すること。

```text
question_id
fingerprint
review finding_code / finding_subject
answer text or structured answer
answered_by
return_state / return_substate / return_phase
artifact versions / hashes
CODE artifact timestamp/hash
REVIEW invocation prompt hash
Q&A answerが次Review promptへ含まれたか
次Review invocationのartifact内容hash
```

特に次を確認する。

- Directorの回答はSQLiteに保存されているか。
- 元質問はANSWEREDまたはPROVISIONAL等の正しい状態へ変わっているか。
- REVIEW再実行時のDirectiveに、その回答または回答による修正結果が入っているか。
- 回答が「説明だけ」で、Reviewerが見ているartifact/codeが変わっていないのに再Reviewしていないか。
- Reviewerの質問がコード/成果物修正を要求する内容なら、Director回答だけでREVIEWへ戻らず、Implementer修正へ送る必要がないか。
- 同じfingerprintの質問を新規question_idとして重複登録していないか。

Controllerが自然言語を解釈して判定してはいけない。必要ならDirectorの構造化結果に「answer only / artifact update required / code update required / upstream change required」等の機械判定可能なactionを追加する。

## 2. Q&A回答の「反映先」を構造化する

Q&A回答後の復帰先を、単純に元REVIEWへ戻すだけにしない。

Director出力は最低限、次のような構造化actionを返せるようにする。

```text
ANSWER_ONLY
IMPLEMENT_CHANGE_REQUIRED
ARTIFACT_CHANGE_REQUIRED
UPSTREAM_CHANGE_REQUIRED
HUMAN_REQUIRED
```

名称は既存設計に合わせて変更してよいが、意味は分離すること。

### ANSWER_ONLY

Reviewerが単に根拠確認を求めており、既存成果物に回答がある場合。

- 回答をSQLiteへ保存
- 次Review Directiveへ回答根拠を含める
- artifact/code変更は不要

### IMPLEMENT_CHANGE_REQUIRED

Reviewerの質問に対する回答によってコード変更が必要な場合。

```text
QANDA
→ Director structured action
→ IMPLEMENT
→ TEST
→ REVIEW
```

Reviewerへ回答文だけ渡して終わらせない。

### ARTIFACT_CHANGE_REQUIRED / UPSTREAM_CHANGE_REQUIRED

正式設計成果物の変更が必要なら、既存Impact Analysisとfreshness処理を使う。

Controllerが自由文から勝手に分類してはならない。

## 3. 同一質問の再発を機械的に検出する

既存fingerprintを利用し、ANSWERED済みの同一質問が同一revision/artifact状態で再発した場合を区別する。

同じ質問が再発したとき、単に新規OPEN questionを増やしてはいけない。

最低限、以下を区別する。

```text
ANSWER_NOT_APPLIED
ANSWER_INSUFFICIENT
ARTIFACT_UNCHANGED_AFTER_REQUIRED_CHANGE
GENUINELY_NEW_CONTEXT
```

これもControllerの自然言語解析ではなく、Director/Reviewerの構造化code + Controllerが知るhash/revisionで判定する。

同一revision・同一artifact hash・同一fingerprintで再発した場合は、無限にQ&Aを増殖させず、既存質問へ再発回数を記録して適切な修正経路へ送る。

## 4. 自律修正ループを実装する

今回の作業そのものも、1回失敗したら終了しない。

以下のループを最大8ラウンド程度の明示的な上限で回す。

```text
run E2E
→ failure/blocker取得
→ JSONL/SQLite/Git状態解析
→ 原因仮説を1つに絞る
→ 最小修正
→ 対象テスト
→ 全pytest
→ 新規scratchでE2E再実行
```

同じ原因fingerprintで2回連続改善がない場合は、同じ修正を繰り返さず別仮説へ進む。

各ラウンドをresultへ記録する。

```text
round
failure point
fingerprint
root-cause hypothesis
changed files
focused test
full pytest
E2E result
next decision
```

## 5. 外側Harnessで途中終了しない実行方法にする

過去に外側PowerShell/exec Harnessの120秒上限で実AI処理が途中終了している。

今回の受入E2Eは、Worker timeoutとは別に十分な外側実行時間を確保する。

重要:

- Worker timeoutをむやみに延長して解決扱いにしない。
- 外側Harness timeoutとWorker timeoutを別々にログする。
- 長時間E2Eを短い監督shellから起動する場合は、子processが監督shell終了でkillされない方法を使う。
- 実AI E2E全体には現実的な総時間上限を設ける（例: 10〜20分）。無制限実行は禁止。
- 進行中のtransition/invocationをJSONL/SQLiteへ逐次flushし、途中終了でも原因追跡できるようにする。

## 6. 2AI受入は「Claude成功必須」にしない

今回の目的は「複数AIオーケストレーションが成立すること」であり、特定CLIの環境不調でMVP全体を永久にblockしない。

同一runで2種類以上の実AIが成功経路に参加すればよい。

優先候補例:

```text
IMPLEMENTER: Codex
REVIEWER: Claude → Codex → Grok
DIRECTOR: Codex → Claude → Grok
```

ただし、ClaudeがtimeoutしてCodexだけで全工程を完了した場合は「2AI COMPLETE」とは数えない。

2種類目のAIが少なくとも1つの**有効なsemantic result**（PASS / DONE / structured Director result等）を返し、その結果がControllerに採用されること。

もしClaudeが環境上安定しない場合、Grokが有効なReviewer/Director結果を返せるかを試す。agyはheadless permission問題が解消していない限り既定routeへ無理に入れない。

## 8. Fake/Scripted統合テストを追加する

通常pytestでは外部AIを使わず、最低限次を固定する。

1. REVIEW QUESTION → Director `ANSWER_ONLY` → same REVIEW → PASS
2. REVIEW QUESTION → Director `IMPLEMENT_CHANGE_REQUIRED` → IMPLEMENT → TEST → REVIEW → PASS
3. 回答済み同一questionが同一revisionで再発してもOPEN行を無限増殖させない
4. required changeなのにartifact/code hashが変わらない場合を検出
5. answer適用後にartifact/hashが変わった場合は新Reviewへ進む
6. fallback後もquestion return position/checkpointを保持
7. 2AI routeの一方失敗→別Worker成功
8. loop guardとQ&A再発guardが衝突しない

通常pytestは外部AI/network非依存を維持する。

修正後、新規scratch Git workspaceで以下を実施する。

### Acceptance A — Codex基準

```text
IDLE → DESIGN → IMPLEMENT → TEST → REVIEW → DOC_SYNC → COMPLETE
```

### Acceptance B — 2AI COMPLETE

同一runで2種類以上の実AIを採用して、COMPLETEまで到達する。

理想例:


### Acceptance C — Q&A収束

実AIで自然なQUESTIONが出た場合は、そのrunを捨てずに可能な限り最後まで継続し、Q&A回答後に同一質問ループが収束することを確認する。

自然にQUESTIONが発生しない場合、Q&A収束はFake/Scripted統合テストの証拠で可とする。QUESTIONを出させるために仕様を壊してはいけない。
