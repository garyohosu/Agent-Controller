# Agent Controller 作業指示書 005

対象: Main Graph 実配線

前提:
- §17-14 Git checkpoint / rollback / Worker fallback は完了済み。
- §17-15 COMPLETE gate は完了済み。
- `instructions/result-2026-08-09-011.md` に記録された COMPLETE gate を迂回してはならない。
- `hikitsugi.md` の「絶対に崩してはいけない 5 つ」を最優先する。

---

## 目的

現在 stub のまま残っている Main Graph の各 State を、既に実装済みの部品へ最小構成で接続し、次の 1 本の流れを実際に通せるようにする。

```text
IDLE
 ↓ START
DESIGN
 ↓ PASS
IMPLEMENT
 ↓ DONE
TEST
 ↓ PASS
REVIEW
 ↓ PASS
DOC_SYNC
 ↓ PASS + COMPLETE gate
COMPLETE
```

今回の目的は新しい大規模抽象化を追加することではない。
これまで個別に確認してきた Controller / DESIGN / Worker / Git checkpoint / TEST / REVIEW / DOC_SYNC / COMPLETE gate を Main Graph 上で接続すること。

---

## 絶対条件

以下は変更しない。

1. Controller は意味を解釈しない。
2. トップレベル State は既存 10 State のまま増やさない。
3. DocumentStage の内部遷移と Main Graph のトップレベル遷移を混ぜない。
4. SQLite を制御状態の正本とする。Markdown を読み戻して状態判定しない。
5. loop guard は Controller が担当し、LangGraph `recursion_limit` は非常停止装置のままにする。
6. COMPLETE への遷移は必ず既存 `CompleteGate` を通す。
7. 実 Worker の異常出力や CLI 失敗で Graph 自体を未記録例外終了させない。
8. 通常の `pytest` を外部 AI CLI 必須にしない。

---

# 1. DESIGN node を実配線する

Main Graph の `DESIGN` node は stub をやめ、既存の `run_design(...)` を呼ぶこと。

実運用では必ず workspace を渡す。
既存の `SPEC.md` 等、人間が用意した成果物を誤って生成から上書きしないこと。

期待する責務:

```text
Main Graph DESIGN
  ↓
run_design(...)
  ↓
DocumentStage Progressive Refinement
  ↓
DESIGN 完了 Event
  ↓
IMPLEMENT
```

DocumentStage 内部の `PASS` を Main Graph の `DESIGN + PASS -> IMPLEMENT` に直接流してはいけない。
設計工程全体が完了したときだけトップレベル Event を返すこと。

DESIGN が以下へ抜ける既存経路も維持する。

```text
HUMAN_REQUIRED
WAIT_RESOURCE
ABORT
```

---

# 2. IMPLEMENT node を実配線する

IMPLEMENT は既存 Worker Interface / Adapter / Git checkpoint を使う。

最低限:

```text
IMPLEMENT 開始
 ↓
Git checkpoint 作成
 ↓
Implementer Worker 実行
 ↓
構造化 WorkerResult を検証
 ├─ DONE                  → TEST
 ├─ QUESTION              → 既存 Q&A loop
 ├─ WORKER_RESOURCE_LIMIT → rollback / Worker fallback / WAIT_RESOURCE
 ├─ WORKER_ERROR          → rollback / fallback / HUMAN_REQUIRED 等の既存方針
 └─ ABORT                  → ABORT
```

Worker の `reason` 自由文を読んで Event を推測してはならない。

`files_changed` は Worker 自己申告を正本にせず、§17-14 の Git 実状態検証を使う。

Implementer の実作業が成功した場合、CODE artifact の鮮度を COMPLETE gate が判定可能な形で更新すること。

---

# 3. TEST node を実配線する

TEST は「AI にテスト結果を判断させる State」にしない。

Controller から明示的な test runner を呼び、終了コード / 構造化結果を元に Event を決める。

最低限:

```text
TEST
 ├─ PASS → REVIEW
 └─ FAIL → IMPLEMENT
```

必要なら TEST_ERROR / WORKER_ERROR 相当の既存 Event へ落としてよいが、自由文解釈で判定しないこと。

TEST PASS は SQLite の transition/event history に正式記録し、§17-15 の鮮度判定に使えること。

古い TEST PASS を再利用しない。
CODE が更新されたら再 TEST が必要。

通常の単体テストでは、実 subprocess を injectable / fake runner に置換できる構造にすること。

---

# 4. REVIEW node を実配線する

REVIEW は既存 Worker Interface を Reviewer role で使う。

可能なら Implementer と Reviewer を別 Worker にする。
ただし Worker availability によって single-agent mode になる場合は既存方針を維持する。

最低限の Event:

```text
REVIEW
 ├─ PASS                      → DOC_SYNC
 ├─ LOCAL_FIX / FIX_REQUIRED  → IMPLEMENT
 ├─ QUESTION                  → Q&A loop
 ├─ UPSTREAM_CHANGE_REQUIRED  → DESIGN / Impact Analysis の既存経路
 ├─ WORKER_RESOURCE_LIMIT     → rollback / fallback / WAIT_RESOURCE
 └─ WORKER_ERROR              → 既存 error path
```

Reviewer が仕様不足を独自解釈して PASS にしないよう、既存 `NO_GUESSING_RULE` / `REVIEWER_RULE` を必ず通す。

REVIEW PASS も SQLite に正式記録し、CODE 更新後の PASS だけが COMPLETE gate を満たすこと。

---

# 5. DOC_SYNC node を実配線する

DOC_SYNC では少なくとも README の同期要否を機械的に扱う。

既存の §17-15 条件に合わせ、README artifact は最終的に次のどちらかになること。

```text
VALID / LATEST
VALID / NOT_REQUIRED
```

README を更新する必要がある場合は Worker に修正させてもよいが、
「README 更新が必要か」という意味判断を Controller が自然言語から行わないこと。
構造化結果を受けて適用する。

DOC_SYNC の `PASS` はそのまま COMPLETE を意味しない。

必ず:

```text
DOC_SYNC + PASS
  ↓
CompleteGate
  ├─ blockers = 0 → COMPLETE
  └─ blockers > 0 → COMPLETE 遷移拒否
```

とする。

既存 `CompleteGateError` 等の仕組みを再利用し、別系統の完了判定を作らない。

---

# 6. Main Graph の例外・中断経路

正常系だけでなく、既に実装済みの次の経路を Main Graph から失わないこと。

```text
WORKER_RESOURCE_LIMIT
  → checkpoint rollback
  → Worker fallback または WAIT_RESOURCE

QUESTION
  → Q&A
  → ANSWERED なら質問元の State / Stage / Phase へ復帰

HUMAN_REQUIRED
  → human answer
  → HUMAN_ANSWER
  → 保存済み return location へ復帰

UPSTREAM_CHANGE_REQUIRED
  → IMPACT_ANALYSIS
  → 必要な設計工程のみ再実行

LOOP_DETECTED / RETRY_LIMIT / NO_PROGRESS
  → HUMAN_REQUIRED
```

中断系 Event を loop count に含めない既存仕様を壊さないこと。

# 7. 最初の Main Graph E2E

実 AI を使う前に、scripted/fake Worker を使った E2E を必ず作る。

最低限、次を 1 本の Main Graph 実行で確認する。

```text
IDLE
→ DESIGN
→ IMPLEMENT
→ TEST
→ REVIEW
→ DOC_SYNC
→ COMPLETE
```

検証項目:

- State Transition Log が上記順序で残る。
- DESIGN 内部の DocumentStage 遷移は top-level State を DESIGN のまま維持する。
- IMPLEMENT 成功で CODE artifact が更新される。
- TEST PASS が CODE 更新後である。
- REVIEW PASS が CODE 更新後である。
- Q&A blocker がない。
- README が LATEST または NOT_REQUIRED。
- Git 条件が満たされる。
- CompleteGate を通って初めて COMPLETE になる。

さらに最低 1 本、gate blocker がある E2E を作り、DOC_SYNC まで進んでも COMPLETE にならないことを確認する。

# 8. 実 AI E2E

scripted/fake E2E が安定してからのみ実施する。

scratchpad workspace を用意し、正式な本リポジトリ成果物を smoke test で汚さないこと。

最初の実 AI E2E は小さなサンプルに限定する。

目標:

```text
既存 SPEC.md
↓ SPEC REVIEW_DEEP
DESIGN 完了
↓
IMPLEMENT
↓
TEST
↓
REVIEW
↓
DOC_SYNC
↓
COMPLETE
```

途中で自然に QUESTION / WORKER_RESOURCE_LIMIT 等が発生した場合は、その実際の結果を優先して記録する。
期待 Event が出るまで入力を作り替えて再試行しないこと。

実 AI E2E が時間・quota・session limit で完走しない場合、それ自体を failure と決めつけない。
State / Event / rollback / resume が正しく記録されたかを result に書く。

# 10. テスト

既存テストをすべて維持する。

最低限追加すること:

1. DESIGN node が `run_design` を呼ぶテスト
2. DESIGN の各 DocumentStage PASS で IMPLEMENT へ早期遷移しないテスト
3. IMPLEMENT → TEST 正常遷移
4. TEST FAIL → IMPLEMENT
5. TEST PASS → REVIEW
6. REVIEW PASS → DOC_SYNC
7. REVIEW fix event → IMPLEMENT
8. REVIEW upstream change → DESIGN/Impact 経路
9. DOC_SYNC PASS + gate success → COMPLETE
10. DOC_SYNC PASS + blocker → COMPLETE 拒否
11. WORKER_RESOURCE_LIMIT 時の rollback / same-location resume
12. Q&A から質問元へ復帰
13. full scripted E2E: IDLE → COMPLETE

通常の:

```bash
uv run pytest -q
```

は Claude Code / Codex CLI / network に依存せず完走すること。

最低限書く内容:

成功したことだけでなく、実 AI をつないで初めて分かった問題も必ず残す。
