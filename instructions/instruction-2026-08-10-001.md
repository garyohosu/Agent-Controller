# 作業指示 001 — v1.1 Acceptance Contract / 決定論的仕様適合検証

## 目的

外部実利用試験 `garyohosu/testproject` で、Agent-Controller は公開 `init` から実AIを起動し、Q&Aを経由して `IDLE → DESIGN → IMPLEMENT → TEST → REVIEW → DOC_SYNC → COMPLETE`、CompleteGate=True まで到達した。

一方、Q&Aで確定した仕様と実装が一致していないにもかかわらず、Reviewer が PASS し CompleteGate も通過した。

確認された不一致:

- JSON必須キー: 期待 `items` / 実装 `todos`
- add出力: 期待 `Added: 1 ...` / 実装 `Added 1: ...`
- done出力: 期待 `Done: 1` / 実装 `Completed 1`

また、Windows cp932 標準出力環境で `agent-controller show` が Q&A 内の Unicode 文字を出力する際に `UnicodeEncodeError` となった。

本指示では、この2点を次版の中核機能として修正する。

最重要目標は、

> AI Reviewer の自然言語 PASS とは独立して、Q&A / SPEC で確定した「機械的に検証可能な仕様」を Acceptance Contract として正規化・保存し、決定論的 Verifier が不一致を検出した場合は COMPLETE を拒否して修正ループへ戻す。

ことである。

---

## 1. 絶対条件

1. トップレベル State は既存の10個を維持する。Acceptance 専用 State を追加しない。
2. Controller は仕様の意味を自然言語から独自解釈しない。
3. AI が仕様から Acceptance Contract 候補を構造化して返し、Controller が schema / provenance / 対象 artifact / verifier 種別を機械的に検証して保存する。
4. Reviewer の `PASS` と Acceptance Contract の `PASS` を混同しない。
5. CompleteGate は、適用対象の必須 Acceptance Contract が未検証または FAIL の場合に COMPLETE を許可しない。
6. Contract FAIL を人間が SQLite 手編集、Markdown手編集、status改ざんで PASS 扱いしてはならない。
7. 通常 pytest は外部AI CLI、ネットワーク、GitHub に依存させない。
8. 実AI受入ではモデル出力を誘導するために入力を何度も改変しない。
9. 既存の SQLite 正本 / Markdown投影 / Git checkpoint / Q&A / guard の原則を維持する。
10. Windows Unicode修正は `PYTHONUTF8=1` 等を利用者に要求するだけの回避策で終わらせない。
11. 作業完了後、結果を `instructions/result-2026-08-10-001.md` に記録し、commit / push、`HEAD == origin/main`、working tree clean まで確認する。

## 3. Acceptance Contract のデータモデル

機械的に検査可能な受入条件を表す型を追加する。

最低限、以下を持つこと。

- contract_id
- run_id
- source_type (`SPEC`, `QANDA`, `TESTCASE`, etc.)
- source_id / source_artifact
- source_revision または provenance
- requirement_kind
- target_artifact / target_scope
- verifier_kind
- verifier_config（構造化JSON）
- required / optional
- status (`PENDING`, `PASS`, `FAIL`, `STALE`, `UNSUPPORTED` 等。既存enum設計に合わせる）
- last_verified_at
- evidence / actual（機械生成）
- failure_code
- created_at / updated_at

ただし、フィールド名・enum名は既存コード規約に合わせてよい。

重要:

- Contract本文を自由文だけで保存しない。
- Verifierが実行できる構造化データを正本とする。
- 人間向け説明文は補助情報にする。

## 4. Contract の生成・更新

### 4.1 Q&Aからの生成

人間またはDirector回答に、明示的で機械検査可能な条件が含まれる場合、AI側に Acceptance Contract 候補を構造化させる。

例:

```json
{
  "requirement_kind": "json_schema_subset",
  "target_artifact": ".todo.json",
  "verifier_kind": "json_shape",
  "verifier_config": {
    "required_keys": ["next_id", "items"]
  }
}
```

```json
{
  "requirement_kind": "cli_stdout",
  "target_artifact": "todo_cli",
  "verifier_kind": "command",
  "verifier_config": {
    "argv": ["python", "-m", "todo_cli", "add", "sample"],
    "exit_code": 0,
    "stdout_pattern": "Added: {id} sample"
  }
}
```

Q&Aの回答全文をControllerが解析してContractを作ってはならない。Workerが構造化候補を返し、Controllerは許可された `verifier_kind` とschemaを検証して保存する。

### 4.2 SPEC / TESTCASEからの生成

SPEC / TESTCASE に明示的な検査可能条件がある場合も同様に候補化できるようにする。

ただし、曖昧な自然言語を無理にContract化しない。検証不能なものはReviewerの意味レビューに残してよい。

### 4.3 provenance / freshness

Contractは元になったQ&A/SPEC/TESTCASEのrevisionまたはfingerprintを保持する。

元仕様が変更された場合、関連Contractは `STALE` または再生成対象とし、古いPASSをそのままCompleteGateで使わない。

## 5. 決定論的 Verifier

Verifier registry / dispatcher を実装する。

MVPとして最低限、今回のTODO受入を検証できる以下を実装する。

### 5.1 JSON shape verifier

- JSONファイルが存在する
- parse可能
- 必須top-level keyの存在
- 必要なら禁止key / primitive type程度まで対応可能
- 実値を evidence に残す

今回必須:

- `next_id`
- `items`

### 5.2 Command verifier

- workspace内で許可されたcommandを実行
- exit code
- stdout
- stderr
- exact / pattern の少なくともどちらか
- timeout

を決定論的に比較する。

今回必須:

- add出力
- done出力
- invalid IDの非0終了 + stderr

### 5.3 File/content verifier（必要なら最小実装）

READMEや `.gitignore` のような静的条件を、exact token / line / regex 等で検査できる最小機構を追加してよい。

### セキュリティ

Contractから任意shell文字列をそのまま実行しない。

- argv配列
- workspace境界
- timeout
- executable allow policy または既存worker/test実行ポリシー

など、既存設計に沿った安全な実行にする。

## 6. TEST / Main Graph への統合

Acceptance verification は新しいトップレベル State にせず、TEST後〜REVIEW/COMPLETE前の既存フローへ統合する。

期待挙動:

```text
IMPLEMENT
  ↓
TEST
  ↓
Acceptance Verify
  ├─ PASS → REVIEW
  └─ FAIL → IMPLEMENT（修正directive付き）
```

または既存構造上より自然なら REVIEW 後に検査してもよいが、最終的に CompleteGate 前には必ず最新Contractを検証済みにする。

### Contract FAIL時

Controllerは意味判断せず、次のような構造化failureを生成する。

- contract_id
- failure_code
- expected
- actual/evidence
- affected target

これを次のIMPLEMENT directiveへ渡す。

例:

```text
ACCEPTANCE_CONTRACT_FAILED
contract=AC-0003
expected required_keys=[next_id, items]
actual keys=[next_id, todos]
```

AI Implementerはそれを修正し、その後TEST + Acceptance Verifyを再実行する。

Guard / NO_PROGRESS と整合させ、同じcontract failureを無限反復しないこと。

## 7. CompleteGate の強化

CompleteGateにAcceptance Contract条件を追加する。

通常production modeでは少なくとも次を満たさない限り COMPLETE 不可。

- required Contract が全件最新
- `PENDING` なし
- `STALE` なし
- `FAIL` なし
- verifier実行証拠あり

blocker codeは機械可読にする。

例:

- `ACCEPTANCE_CONTRACT_PENDING`
- `ACCEPTANCE_CONTRACT_FAILED`
- `ACCEPTANCE_CONTRACT_STALE`
- `ACCEPTANCE_VERIFIER_UNSUPPORTED`

名称は既存規約に合わせてよい。

ReviewerがPASSでもContract FAILならCompleteGateは必ず拒否すること。

## 9. Windows Unicode-safe CLI output

Windows cp932環境でも `status`, `questions`, `show`, `contracts` 等が Unicode を含むSQLite/Markdown内容で落ちないよう修正する。

要件:

- `UnicodeEncodeError` でプロセスが落ちない
- UTF-8 capable terminalではUnicodeを保つ
- cp932で表現不能文字がある場合も、安全に出力または適切なfallbackを行う
- 既存JSON/機械可読出力を壊さない
- secretやバイナリを誤ってescape表示しない

実装方法はPython標準I/Oの `reconfigure(errors=...)`、安全なwriter、encoding検出等から選んでよいが、Windowsだけの ad-hoc print置換を各コマンドに重複させない。

Windows相当のencodingを模擬するunit testを追加すること。

## 11. 実AI外部受入

実装・unit/integration完了後、`garyohosu/testproject` を用いて新規runで再受入する。

既存の成功済みTODO成果物をそのまま再利用してPASSさせない。必要なら新規scratch clone / 新規branch / 新規run IDを使い、Git安全条件を守る。

要求は前回と同程度のTODO CLIでよい。

人間Q&Aが自然発生した場合は、人間が回答するまでHUMAN_REQUIREDで止める。モデルにQUESTIONを強制するため入力を歪めない。

受入で確認すること:

1. 公開 `init` から開始できる
2. 実AI IMPLEMENTが走る
3. ContractがSQLiteに保存される
4. わざと人間が成果物を壊してFAILを作ることは禁止
5. 自然な実装がContract違反ならVerifierが検出する
6. 違反時は修正loopへ戻る
7. 最終Contract全PASS
8. Reviewer PASS
9. CompleteGate=True
10. COMPLETE
11. Windows cp932相当で `show` が落ちない

自然な初回実装が最初からContractを満たした場合、それは成功としてよい。その場合、Contract FAIL→repair loopの証拠はfake integration testで担保する。

## 12. 既存設計を壊さないための注意

- `TRANSITIONS` と `STAGE_TRANSITIONS` を混ぜない。
- トップレベルState追加禁止。
- Controllerが自然言語仕様を意味解釈しない。
- Markdownを正本にしない。
- QandA.mdを読み戻してContract生成しない。SQLiteのQ&A正本を使う。
- Reviewerの自由文をContractのactual判定に使わない。
- Worker self-reportのartifact/stageを制御データとして信用しない。
- Acceptance ContractのFAILはguard fingerprintに利用できる安定したmachine codeを持たせる。
- Contractの更新で過去証拠を破壊せず、少なくとも監査可能な履歴またはprovenanceを残す。
