# Agent Controller 実装指示書 001

## 目的

`memo.md` の設計方針を基に、Agent Controller の最初の実装を開始する。

本プロジェクトの目的は、従来人間が行っていた「ChatGPT と相談 → CLI AI へ指示を転記 → QandA.md を確認 → ChatGPT に回答させる → CLI AI へ再指示」という往復を、決定論的な State Machine と Director / Implementer / Reviewer の AI Worker により自動化することである。

既存の `spec-to-design` 的な逐次設計の長所は残しつつ、State Machine によって安全に機能を増やす。

---

## 最重要設計原則

### 1. トップレベル State を増やしすぎない

トップレベル Graph は可能な限り単純にする。

概念上は以下程度を基本とする。

```text
IDLE
DESIGN
IMPLEMENT
TEST
REVIEW
DOC_SYNC
COMPLETE
HUMAN_REQUIRED
WAIT_RESOURCE
ABORT
```

`SPEC_CREATE`、`USECASE_CREATE`、`SEQUENCE_REVIEW` 等をすべてトップレベル State として横並びにしない。

繰り返し処理は Subgraph / Substate として実装すること。

---

### 2. DESIGN は階層 State / Subgraph とする

設計工程は次の段階的詳細化を行う。

```text
SPEC
 ↓
USECASE
 ↓
SEQUENCE
 ↓
CLASS
 ↓
UI（必要な場合）
 ↓
TESTCASE
```

これは単なる文書生成ではない。

各工程で上位成果物をより細かい粒度へ再設計する **Progressive Refinement（段階的詳細化）** と位置付ける。

各工程を進むほど具体化されるため、上位仕様の曖昧さ・矛盾・不足を実装前に発見しやすくすることが目的である。

ただし通常は、各 Document Stage の中で上位工程へ安易に戻らない。

通常の修正は現在の成果物内で完結させる。

```text
CLASS/REVIEW
  ↓ LOCAL_FIX
CLASS/FIX
```

重大な上位矛盾が見つかった場合のみ、通常の局所修正とは別イベントを発生させる。

```text
UPSTREAM_CHANGE_REQUIRED
```

その場合は後述の `IMPACT_ANALYSIS` を通して必要最小限の上位工程へ戻す。

---

### 3. Document Stage を共通化する

SPEC / USECASE / SEQUENCE / CLASS / UI / TESTCASE ごとに別々の状態機械を大量実装しない。

可能な限り共通の Document Stage Subgraph を用意し、設定値で振る舞いを変える。

概念：

```text
DOCUMENT_STAGE
    ↓
GENERATE
    ↓
REVIEW
    ├─ PASS → COMPLETE
    ├─ LOCAL_FIX → FIX → REVIEW
    ├─ QUESTION → ANSWER_QUESTION → 再開
    └─ SERIOUS_ISSUE → IMPACT_ANALYSIS
```

想定設定例：

```python
DocumentStage(
    name="CLASS",
    inputs=["SEQUENCE.md", "SPEC.md"],
    output="CLASS.md",
    review_level="LIGHT",
    max_review_retry=2,
)
```

共通化によって State 数・コード量・条件分岐を減らすこと。

## レビュー戦略

### 4. FAST PATH と DEEP PATH

以前の設計自動化が重くなりすぎた反省から、毎回すべてを詳細レビューしない。

通常は FAST PATH を使う。

```text
GENERATE
 ↓
REVIEW_LIGHT
 ├─ PASS → 次工程
 ├─ LOCAL_FIX → FIX → REVIEW_LIGHT
 └─ SERIOUS_ISSUE → REVIEW_DEEP / IMPACT_ANALYSIS
```

軽量レビューで重大な疑いが出た場合だけ DEEP PATH を使用する。

```text
REVIEW_DEEP
 ↓
DIRECTOR
 ↓
REWORK
 ↓
REVIEW_DEEP
```

毎回 DEEP REVIEW を行わないこと。

### 5. レビュー強度

初期値として以下を参考にする。

```text
SPEC      DEEP
USECASE   DEEP
SEQUENCE  LIGHT
CLASS     LIGHT
UI        LIGHT
TESTCASE  LIGHT
```

ただし State Machine により必要時には LIGHT → DEEP へ昇格可能にする。

再レビュー時は前回指摘の解消確認を優先し、新しい論点を無制限に増やさない。

## 影響範囲分析

### 6. IMPACT_ANALYSIS を正式な処理として実装する

上位成果物の変更が必要になった際、依存する下流成果物を機械的に全部作り直さない。

変更内容を Director / Impact Analyzer が評価し、各成果物に状態を付ける。

最低限：

```text
VALID
REVIEW_REQUIRED
STALE
```

意味：

```text
VALID           影響なし。処理不要
REVIEW_REQUIRED 影響の可能性あり。軽量レビューのみ
STALE           影響あり。再生成または修正が必要
```

例：

```text
SPEC変更
 ↓
IMPACT_ANALYSIS
 ↓
USECASE    VALID
SEQUENCE   REVIEW_REQUIRED
CLASS      STALE
UI         VALID
TESTCASE   STALE
CODE       STALE
README     STALE
```

Controller は最も上流の `STALE` / 必要な `REVIEW_REQUIRED` から再開する。

影響分析結果と再開理由は必ずログへ残す。

## Director / Implementer / Reviewer

### 7. Director を人間と CLI AI の間の通訳役にする

Director は次の役割を持つ。

- 上位仕様・設計成果物を読む
- Implementer がそのまま実行できる具体的指示を生成する
- Reviewer の指摘を意味解釈する
- QandA.md の質問へ、既存成果物から回答する
- 必要に応じて修正指示を Implementer へ再発行する
- 上位変更が必要なら `UPSTREAM_CHANGE_REQUIRED` 等のイベントを返す
- 自分で State 遷移を自由決定しない

工程遷移は Controller が決定する。

```text
current_state + event -> next_state
```

Director は意味判断、Controller は工程制御と責務分離する。

### 8. 中心ループ

以下を人間のコピペなしで回せるようにする。

```text
上位仕様
 ↓
DIRECTOR
 ↓ 指示
IMPLEMENTER
 ├─ DONE
 │    ↓
 │  TEST
 │    ↓
 │  REVIEWER
 │    ├─ PASS → 次工程
 │    └─ QUESTION / FAIL
 │          ↓
 │       DIRECTOR
 │          ↓ 修正指示
 │       IMPLEMENTER
 │          ↓
 │       REVIEWER
 │
 └─ QUESTION
      ↓
   QandA.md
      ↓
   DIRECTOR
      ↓ 回答・追加指示
   IMPLEMENTER
```

Reviewer の質問に対してコード修正が必要と Director が判断した場合、Reviewer に直接回答して終了せず、必ず Implementer へ修正指示 → 再レビューとする。

## QandA.md

### 9. Agent 間の正式な問い合わせチャネル

Implementer / Reviewer / Designer 等は判断不能な内容を `QandA.md` に記録する。

最低限保持する項目：

```text
Question ID
Questioner Role
Questioner Worker
Current State / Substate
Question
Reason / Context
Status: OPEN / ANSWERED / HUMAN_REQUIRED
Answer
Answered By
Related Artifacts
```

Director が既存成果物から回答できる場合は回答し、元 State / Substate に戻す。

正式仕様に情報が存在せず推測が必要な場合のみ `HUMAN_REQUIRED` とする。

## ログ

### 10. 状態遷移ログを最優先で実装する

人間が真っ先に見るログは State Transition Log とする。

すべての遷移について最低限以下を記録する。

```text
timestamp
run_id
state
substate
phase
from_state
from_substate
event
to_state
to_substate
role
worker
reason
retry_count
checkpoint_commit
```

人間向け表示例：

```text
19:10:12 | DESIGN/CLASS/REVIEW | LOCAL_FIX
         -> DESIGN/CLASS/FIX | worker=codex | retry=1

19:13:44 | DESIGN/CLASS/REVIEW | UPSTREAM_CHANGE_REQUIRED
         -> IMPACT_ANALYSIS | reason=sequence responsibility mismatch

19:14:02 | IMPACT_ANALYSIS | RESULT
         CLASS=STALE TESTCASE=STALE CODE=STALE README=STALE
         -> DESIGN/CLASS/GENERATE
```

SQLite の Event History を正本とし、人間向けテキストログを生成可能にする。

## 無限ループ防止

### 11. Controller に機械的 Guard を持たせる

AI に無限ループ判定を任せない。

最低限：

- State / Substate ごとの retry 上限
- 同一遷移の連続回数上限
- 1 run の最大 transition 数
- 同一 Q&A の再発検出
- 同一 test failure / review finding の繰り返し検出
- `NO_PROGRESS` fingerprint
- Worker を変更しても同一失敗なら `HUMAN_REQUIRED`
- 同一理由による上位手戻りの繰り返しは `LOOP_DETECTED`

上限値は設定可能にする。

## Git checkpoint / Worker fallback

### 12. State 開始時 commit SHA を必ず記録する

```text
State/Substate 開始
 ↓
clean tree 確認
 ↓
checkpoint commit SHA 記録
 ↓
Worker 実行
 ↓
成功時のみ commit + push
```

Session limit / token limit / rate limit / CLI crash の場合：

```text
WORKER_RESOURCE_LIMIT / WORKER_ERROR
 ↓
開始時 checkpoint まで rollback
 ↓
Worker 切替
 ↓
同一 State/Substate を再実行
```

単に現在の HEAD へ戻すのではなく、開始時に保存した SHA を使うこと。

`git clean -fd` を無条件使用しない。

### 13. Worker 優先順位

初期 Worker：

```text
Claude Code
Codex CLI
AntiGravity
Grok
```

通常は Claude Code と Codex CLI を優先する。

可能なら Implementer と Reviewer は別 Worker にする。

片方が利用不能なら single-agent mode を許可するが、品質モードを記録する。

```text
DUAL_AGENT
SINGLE_AGENT
FALLBACK_AGENT
```

## README / 完了条件

### 14. README.md を正式成果物として扱う

特に以下では README 更新要否を必ず判定する。

```text
SPEC_CHANGE
USECASE_CHANGE
公開 API / CLI 変更
設定方法変更
インストール方法変更
ユーザー向け動作変更
```

`DOC_SYNC` 内で README を同期し、必要ならレビューする。

### 15. COMPLETE 条件

最低限：

```text
必要な設計成果物が VALID
CODE latest
README latest（更新不要判定も可）
TEST PASS
REVIEW PASS
QandA OPEN = 0
working tree clean
commit 済み
push 済み
```

## 実装方針

### 16. 技術

以下を使用する。

- Python
- LangGraph
- Pydantic
- SQLite

過度な抽象化は避ける。

「将来必要かもしれない」だけの複雑な汎用フレームワークを先に作らない。

**シンプルな Main Graph + 小さな Subgraph + 明示的 Event** を優先する。

### 17. 最初の実装順

一度に全機能を完成させない。

以下の順で進めること。

1. プロジェクト骨格
2. Pydantic の State / Event / ArtifactStatus モデル
3. SQLite 永続化
4. State Transition Logger
5. 小さい Main Graph
6. 共通 DocumentStage Subgraph
7. DESIGN の Progressive Refinement
8. LIGHT / DEEP review routing
9. retry / loop guard
10. IMPACT_ANALYSIS
11. Director / Implementer / Reviewer 共通 Worker interface
12. Claude Code / Codex CLI adapter
13. QandA loop
14. Git checkpoint / rollback / fallback
15. README / COMPLETE gate
16. AntiGravity / Grok fallback は後から追加可能

まず Controller と State Machine の正しさを優先し、実 AI 接続を先行させすぎない。

## 最初の実証

最初の E2E は小さなサンプルを使い、少なくとも以下を確認する。

```text
DESIGN
  └─ DocumentStage
       GENERATE
       → REVIEW_LIGHT
       → LOCAL_FIX
       → PASS

IMPLEMENT
 → TEST
 → REVIEW
 → DOC_SYNC
 → COMPLETE
```

追加テストとして最低限以下を行う。

- QUESTION → Director Answer → 元工程再開
- SERIOUS_ISSUE → IMPACT_ANALYSIS → 必要工程だけ再実行
- REVIEW_FAIL が続く → LOOP Guard 発火
- Worker resource limit → rollback → Worker 切替 → 再実行
- 状態遷移ログから「どの State で、どの Event により、どこへ戻ったか」が追跡可能

## 既存 memo.md について

`memo.md` は設計メモとして参照する。

実装中に本指示書との違いが見つかった場合、より新しい本指示書の方針を優先する。

特に、`memo.md` にある多数のトップレベル State 案は、そのまま実装せず、今回決定した **階層 State / Subgraph を使った簡素な構造**へ整理すること。

また、設計工程は単なる文書生成ではなく、上位仕様を段階的に再設計・詳細化し、実装前に矛盾を発見する工程として実装する。

---

## 成果物

作業完了時に以下を必ず作成すること。

```text
result-2026-08-08-001.md
```

結果ファイルには最低限以下を書く。

- 実施内容
- 実装した State / Substate / Event
- Mermaid による実装後の State Machine 図
- 追加・変更ファイル
- テスト結果
- E2E 実行結果
- 状態遷移ログ例
- 未実装事項 / 制約
- 次に行うべき作業
- 最終 commit SHA
- `git status --short` の結果

---

## Git 最終処理

作業完了時は必ず以下を実施する。

1. 全テストを実行する
2. `result-2026-08-08-001.md` を更新する
3. `git status` を確認する
4. 必要な変更を commit する
5. `origin/main` へ push する
6. push 後の commit SHA を result に記録する
7. 最終的に `git status --short` が clean であることを確認する

途中で問題が発生した場合も、推測で危険な操作をせず、実施済み内容・停止理由・再開方法を result に記録すること。
