# 作業指示 018 — フィールドテスト結果を反映した自律性改善

## 目的

`needs-detector` を実際の外部プロジェクトとして Agent-Controller で開発したフィールドテストにより、Controller が安全に停止できる一方で、**人間への問い合わせが多く、ユーザーが放置して開発を進めにくい**ことが確認された。

今回の目的は、Agent-Controller を「安全に止まるController」から、**通常は自律的に進み、危険・不可逆・本当に仕様判断が必要なときだけ人間を呼ぶController**へ改善することである。

ユーザー価値は明確である。

> 楽をしたい。普段は放置できて、危ない時だけ呼ばれる開発ワークフレームにする。

この方針を最優先とする。

---

## 1. フィールドテストで確認された問題

対象フィールドテスト:

```text
workspace: C:\PROJECT\needs-detector
run: NEEDS-CPF-GATE-002
```

Agent-Controller 自身の通常テストは以下の状態で開始された。

```text
280 passed, 4 skipped
```

しかし実プロジェクトでは、次のような停止が連続した。

### 1.1 軽微な仕様判断でも HUMAN_REQUIRED

例:

- 既存 `evaluate_cpf()` の flat dict 契約を維持するか、新しい nested shape にするか
- `cpf_blockers` の具体値
- `doctor --json` の検査範囲
- Evidence Gate を `next` にも反映するか、`report / doctor` のみにするか

これらの一部は、人間に聞かなくても一般的な保守方針で安全に決められる。

### 1.2 小規模改修でも Progressive Refinement を全段通ろうとする

今回の `needs-detector` 変更は、既存CLIに Evidence Gate を追加する限定改修である。

しかし現在の DESIGN は概ね次を順番に要求する。

```text
SPEC -> USECASE -> SEQUENCE -> CLASS -> UI -> TESTCASE
```

その結果、今回の変更では不要性が高い USECASE 生成まで進み、そこで停止した。

### 1.3 WRITE_PERMISSION_DENIED から自動復旧しない

USECASE生成Workerで `WRITE_PERMISSION_DENIED` が繰り返され、同じ障害が3回継続した後に HUMAN_REQUIRED / BLOCKED となった。

書き込みが必要な成果物生成であれば、read-only Workerへの再試行ではなく、write-capable Workerへ自動fallbackすべきである。

### 1.4 Workerごとの能力差を十分に扱えていない

Claude Code / Codex CLI 等は同じWorkerではない。

ツール権限、write/readの扱い、長文prompt、timeout傾向、plan mode等に差がある。

Controllerは「交換可能なAI」として抽象化しつつも、**能力差は明示的なCapabilityとして扱う**必要がある。

---

# 2. 今回の改善範囲

今回は次の3機能を優先実装する。

```text
A. Task Complexity Router / Design Fast Path
B. Auto-Recovery Policy
C. Default Decision Policy
```

加えて、A/Bを支える最小限の Worker Capability Profile を導入してよい。

全部を巨大な自律エージェント機構へ作り替えない。

既存State Machine、SQLite canonical、CompleteGate、Q&A、Git安全機構を維持する。

---

# 3. A: Task Complexity Router / Design Fast Path

## 3.1 目的

全タスクを同じDESIGN工程へ通さない。

初期要求と既存workspaceの状態から、Controller / Director がタスク種別を構造化して提案し、Controllerが許可された経路へルーティングする。

最低限、以下の分類を扱う。

```text
NEW_PRODUCT
NEW_FEATURE
SMALL_FEATURE
BUG_FIX
REFACTOR
DOC_ONLY
```

名称は既存モデルと整合するよう変更してよい。

## 3.2 推奨経路

### NEW_PRODUCT

```text
SPEC -> USECASE -> SEQUENCE -> CLASS -> UI -> TESTCASE
```

UIが存在しない製品ではUIを必須にしない設計でもよい。

### NEW_FEATURE

```text
SPEC -> USECASE -> TESTCASE
```

SEQUENCE / CLASS / UI は影響範囲に応じて必要時のみ。

### SMALL_FEATURE

```text
SPEC -> TESTCASE
```

既存設計を変更しない小規模機能では USECASE / SEQUENCE / CLASS / UI をスキップできる。

### BUG_FIX

```text
REPRO / SPEC -> TESTCASE
```

再現条件とAcceptance Contractを優先する。

### REFACTOR

```text
SPEC -> TESTCASE
```

外部挙動を変えないことをAcceptance Contractで保証する。

### DOC_ONLY

```text
SPEC -> REVIEW
```

実装工程を通さない。

## 3.3 重要原則

- Fast Pathは安全機構を飛ばす機能ではない。
- Acceptance Contract、TEST、REVIEW、CompleteGateは維持する。
- 単に「文書を少なくする」ための機能であり、品質ゲートを削除しない。
- Task Typeが不明でも、保守的な既定値で進められる場合はHUMAN_REQUIREDにしない。
- NEW_PRODUCT相当か既存システム破壊を伴う可能性が高い場合のみ、必要なら人間へ確認する。

---

# 4. B: Auto-Recovery Policy

## 4.1 目的

既知の実行エラーで即HUMAN_REQUIREDにせず、Controllerが決定論的に復旧を試みる。

自然言語で「頑張って再試行」させるのではなく、エラー種別とWorker Capabilityに基づく機械的ルートとする。

## 4.2 最低限の復旧規則

### WRITE_PERMISSION_DENIED

```text
current worker fails
-> 同一workerへの単純再試行を停止
-> can_write=true の候補へfallback
-> 全write-capable候補失敗時のみ HUMAN_REQUIRED
```

### READ_PERMISSION_DENIED

```text
-> can_read=true のReviewer/Director候補へfallback
-> 全候補失敗時のみ HUMAN_REQUIRED
```

### TIMEOUT

既存のtimeout/fallback設計を尊重しつつ、必要なら次を行う。

```text
1. 同じcheckpointを維持
2. prompt短縮契約がある場合は短縮版
3. 別Workerへfallback
4. 上限到達時のみ HUMAN_REQUIRED
```

無限再試行は禁止。

### RATE_LIMIT / RESOURCE_LIMIT

別AI Workerが利用可能ならfallbackする。

全候補が同じ制限ならHUMAN_REQUIREDまたは明示的BLOCKEDへ進む。

### dirty workspace

これは自動回避しない。

```text
dirty workspace -> HUMAN_REQUIRED / BLOCKED
```

`git clean`, `reset --hard`, stash, 未追跡ファイル削除等を自動実行しない。

この安全性は今回の改善後も維持する。

## 4.3 Recovery履歴

復旧試行は診断ログへ残す。

最低限:

```text
error code
failed worker
failed role
capability mismatch
fallback worker
attempt number
final outcome
```

同一原因の再試行を回数だけ増やさない。

---

# 5. Worker Capability Profile

Auto-Recoveryとroutingに必要な範囲で、Workerごとの能力を構造化する。

例:

```text
can_read
can_write
can_review
can_implement
can_answer
supports_plan_mode
supports_structured_output
```

必要ならruntime diagnosticsとして以下を持ってよい。

```text
recent_timeout_count
recent_permission_denied_count
recent_success_count
```

ただし今回は高度な学習型ルーターまでは必須にしない。

まずは**静的Capability + Run内の明白な失敗履歴**で十分。

### 原則

- Role名だけでwrite可能と仮定しない。
- 成果物生成は `can_write=true` のWorkerだけを候補にする。
- Reviewerは原則read-onlyを維持する。
- read-only Workerの権限を自律性のために安易に広げない。

---

# 6. C: Default Decision Policy

## 6.1 目的

軽微で可逆な設計判断のたびに人間を呼ばない。

Controllerが採用可能な「既定の意思決定原則」を明示する。

最低限、次を既定方針とする。

```text
1. 既存API / データ互換を優先
2. 最小変更を優先
3. 要求スコープを広げない
4. 不明なら保守的な側へ倒す
5. 可逆な判断は自動決定して記録
6. 既存テスト・既存挙動を維持
7. 新しい公開契約を増やすより既存契約に合わせる
8. 同一Runで人間が回答した方針を、同種判断へ再利用
```

## 6.2 HUMAN_REQUIREDに残す判断

次は原則として人間へ上げる。

```text
破壊的変更
不可逆操作
既存公開APIの意図的破壊
データ削除・migrationで情報損失の可能性
security / privacy上の重大判断
費用発生
外部公開・release・deployment
要求同士が本質的に矛盾している場合
複数案があり製品価値を大きく変える仕様判断
```

### 逆に人間へ聞かない例

今回のfield testで発生した次の判断は、原則自動決定対象とする。

```text
既存flat APIを維持するか -> 維持
nextまで変更範囲を広げるか -> 広げない
小規模改修でUSECASE/CLASS/UIを全部生成するか -> 必要なければskip
```

## 6.3 Decision Log

自動判断は隠さない。

```text
decision
policy rule
alternatives considered
why no human escalation was required
```

をSQLiteまたは既存の正本設計に整合する形で残す。

Markdownだけを正本にしない。

---

# 7. 同一Run内の回答再利用

Q&Aで一度人間が示した一般方針は、同じRun中の同種判断へ利用可能にする。

例:

```text
「既存API互換を優先」
```

という人間回答があれば、その後の軽微なshape変更判断で同じ質問を繰り返さない。

ただし質問固有の値を無関係な判断へ拡張しない。

構造化されたdecision scopeを持たせること。

3. 小規模改修で不要なUSECASE / SEQUENCE / CLASS / UIのskip

# 9. Acceptance Contract

最低限、次を自動テストする。

## AC-01 SMALL_FEATURE Fast Path

SMALL_FEATURE相当のfixtureで、不要なUSECASE / SEQUENCE / CLASS / UIを生成せず、必要なSPEC / TESTCASEからIMPLEMENTへ進める。

## AC-02 NEW_PRODUCTは従来のProgressive Refinementを維持

Fast Path追加で既存フル設計経路を壊さない。

## AC-03 WRITE_PERMISSION_DENIED fallback

最初のWorkerがwrite不可の場合、同一Workerへ3回繰り返すのではなく、write-capable Workerへfallbackする。

## AC-04 全write候補失敗

全write-capable Workerが失敗した場合のみHUMAN_REQUIREDになる。

## AC-05 dirty workspace

dirty workspaceは従来通り安全に拒否し、自動cleanしない。

## AC-06 Default Decision: backward compatibility

既存API維持 vs 新shapeのような軽微・可逆判断で、既存互換優先ルールにより自動決定できる。

## AC-07 Scope expansion prevention

要求にない追加機能を作る選択肢が出た場合、既定でスコープを広げない。

## AC-08 Decision Log

人間問い合わせを省略した自動判断について、どのpolicyで決定したか追跡可能。

## AC-09 Existing tests

通常pytestがすべて成功する。

## AC-10 field regression

needs-detector field testで、旧Runより不要なHUMAN_REQUIREDが減ることを記録する。

単に質問を握り潰すことで達成しない。

---

# 10. 禁止事項

- HUMAN_REQUIREDを全面禁止する
- 安全確認をなくす
- dirty workspaceを自動cleanする
- Reviewerへ無制限write権限を与える
- 全エラーをCodexへ投げればよいという固定実装にする
- Claude / Codex等を名前だけで永久固定する
- 無限fallback
- 同じ失敗を同じ条件で繰り返す
- Fast PathでTEST / REVIEW / CompleteGateまで省略する
- 既存full DESIGN flowを削除する
- AI自然言語だけでTask Typeや権限を確定し、その検証をしない

# 14. 最終目標

Agent-Controllerの価値は「たくさん質問して安全に止まること」ではない。

目標は次である。

> **普段は放置できる。既定方針で安全に判断し、既知エラーから自動復旧し、本当に人間しか決められない時だけ呼ぶ。**

今回のfield testで見つかった停止は不具合隠しをせず、Agent-Controller自身を改善するための受入材料として利用すること。
