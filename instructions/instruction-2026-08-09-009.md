# 作業指示 009 — 1問ごとに停止しないためのバッチ判断・自律継続

## 目的

指示書008の実AI E2Eでは、Codex単独の安定構成でも `DESIGN/USECASE` で仕様未決定を検出し、Q&Aが `CANNOT_ANSWER` となって `HUMAN_REQUIRED` へ停止した。

この安全停止自体は正しいが、今後も設計上の細かな未決定事項が出るたびに1件ずつ人間へ戻ると、自動開発ループとして実用にならない。

今回の目的は、**推測禁止を維持したまま、低リスク・可逆な未決定事項はController管理下の明示的な暫定判断として継続し、人間確認が必要な事項はまとめて一度に提示すること**である。

最重要目標は次の2つ。

1. 1件の質問ごとに `HUMAN_REQUIRED` で停止しない。
2. 人間判断が本当に必要な場合でも、可能な限り質問をまとめ、設計工程の境界で1回だけ停止する。

これは「AIに勝手に仕様を決めさせる」機能ではない。判断の根拠・分類・暫定性を構造化し、後から人間が監査・変更できる形にする。

---

## 前提

指示書008 / result-2026-08-09-015.md の内容を前提とする。

現在確認済み:

- `SPEC/REVIEW_DEEP`: Claude / Codex / Grok がPASS可能。
- `USECASE/GENERATE`: CodexでDONE。
- `USECASE/REVIEW_DEEP`: Codexが仕様未決定をQUESTIONとして正しく検出。
- 問題例: `greet NAME` において empty name と missing argument の扱いが正式成果物に定義されていない。
- 現状のQ&Aは正式成果物に根拠がなければ `CANNOT_ANSWER -> HUMAN_REQUIRED` となる。
- Main Graph / CompleteGate / Git checkpoint / 4AI Adapter / WorkerRouter は既存実装を壊さない。

---

## 絶対条件

以下を崩してはならない。

1. Controllerは自然言語の意味を解釈して仕様決定しない。
2. 正式成果物に根拠がある場合は、それを最優先して従う。
3. AIが自由文で勝手に仕様を確定してはならない。
4. 暫定判断は必ず構造化データとして保存し、根拠・リスク・可逆性・影響範囲を残す。
5. 高リスクな未決定事項は従来どおり人間へ送る。
6. `COMPLETE` は既存CompleteGateを必ず通す。
7. トップレベルStateは増やさない。
8. SQLiteを正本とし、Markdownは投影とする。
9. 特定Eventを出させるために入力文を何度も変更しない。
10. 通常pytestは外部AI CLI / networkに依存させない。

## 1. 未決定事項の分類を追加する

QUESTION / CANNOT_ANSWER が発生したとき、即座に `HUMAN_REQUIRED` へ送る前に、Director相当の判断ステップを1回入れる。

Controller自身は分類しない。AI Directorが構造化結果を返し、Controllerがschema検証して適用する。

最低限、次の分類を持つこと。

```text
DECIDABLE_FROM_ARTIFACT
LOW_RISK_REVERSIBLE
HIGH_RISK_PRODUCT_DECISION
EXTERNAL_CONTRACT
SECURITY_OR_SAFETY
IRREVERSIBLE_OR_DATA_LOSS
UNKNOWN
```

意味:

- `DECIDABLE_FROM_ARTIFACT`
  - 既存成果物に答えがある。
  - Directorが対象文書と根拠箇所を示してANSWERし、通常フローへ戻る。

- `LOW_RISK_REVERSIBLE`
  - 小さなCLI挙動、内部命名、表示文言、局所的エラーコード、容易に変更できるデフォルト等。
  - 暫定判断を許可する。

- `HIGH_RISK_PRODUCT_DECISION`
  - 製品の意味・ユーザー体験・課金・公開API・互換性など、後工程へ広く影響する判断。
  - 人間確認対象。

- `EXTERNAL_CONTRACT`
  - 外部API、法令、顧客要求、既存公開仕様など。
  - 根拠なしに暫定決定しない。

- `SECURITY_OR_SAFETY`
  - 認証、権限、秘密情報、破壊操作、安全性。
  - 暫定決定しない。

- `IRREVERSIBLE_OR_DATA_LOSS`
  - データ削除、migration不可逆、破壊的Git操作など。
  - 暫定決定しない。

- `UNKNOWN`
  - 分類不能。
  - 人間確認対象。

## 2. LOW_RISK_REVERSIBLE だけ暫定判断を許可する

`LOW_RISK_REVERSIBLE` の場合のみ、Directorは次の構造を返せるようにする。

```json
{
  "decision_class": "LOW_RISK_REVERSIBLE",
  "question_id": "Q-xxxx",
  "provisional_answer": "...",
  "rationale": "...",
  "affected_artifacts": ["SPEC", "USECASE"],
  "reversible": true,
  "risk": "LOW",
  "requires_human_confirmation_before_complete": true
}
```

Controllerはこれを検証し、SQLiteへ「暫定判断」として保存する。

重要:

- これは正式仕様の確定ではない。
- 質問statusを通常ANSWEREDと混同しない。
- 例: `PROVISIONAL` など明確に別状態/別fieldで管理する。
- QandA.mdには「暫定」「人間未承認」を明示して投影する。
- 暫定判断を使って後続設計を進めてもよい。
- 暫定判断から生成・修正されたartifactには、そのprovisional decision IDとの関連を残す。

### 今回の例

`missing argument` と `empty string` の扱いのような、scratch用の小さなCLI仕様で、変更容易・外部契約なし・安全性影響なしなら、Directorが `LOW_RISK_REVERSIBLE` と判定できる設計にする。

ただし、「missing argumentはexit 2にする」といった具体値をControllerコードへハードコードしてはいけない。AI Directorの構造化判断として記録する。

## 3. 質問を1件ずつHUMAN_REQUIREDにしない

高リスクまたは人間確認必須の質問が出ても、直ちにトップレベル `HUMAN_REQUIRED` へ遷移するのではなく、可能な範囲で質問を蓄積する「batch pending」動作を追加する。

### 原則

- 同じDocumentStage内で独立して処理可能な作業は続ける。
- その質問が次工程の意味を決めないと進めない場合は、そのstageだけ止める。
- すぐにMain Graph全体を終了しない。
- 可能なら同stage/同設計系列で他の未決定事項もDirector/Reviewerに洗い出させる。
- 人間へ出すときは1件ずつではなく、未解決質問をまとめて提示する。

### HUMAN_REQUIREDへ遷移するタイミング

次のいずれかに限定する。

1. 現在stageが人間判断なしではこれ以上進められず、追加質問の洗い出しも完了した。
2. HIGH_RISK等の質問が設計全体の上流を塞いでいる。
3. loop guard / no-progress条件に達した。
4. 実装開始前の「human decision gate」に到達した。
5. COMPLETE前に未承認provisional decisionが残っている。

これにより、1問発見ごとの停止を避ける。

## 4. Human Decision Batch を実装する

SQLite canonicalで、人間確認待ちの質問・暫定判断をまとめて取得できるようにする。

最低限CLIで次を表示可能にする。

```text
agent-controller --run RUN questions
```

または既存コマンド拡張で、次を区別して表示する。

```text
OPEN
PROVISIONAL
HUMAN_REQUIRED
ANSWERED
```

バッチ表示では各項目について最低限以下を示す。

```text
question_id
source state/stage/phase
question
classification
provisional_answer (if any)
risk
reversible
blocking_scope
recommended_human_action
```

人間が複数回答をまとめて入力できる手段も追加する。

例:

```text
agent-controller --run RUN answer-batch answers.json
```

または同等の安全なCLI。

既存の1件回答CLIは互換のため残してよい。

## 5. provisional decisionの承認境界

暫定判断を許可しても、最終的に人間未承認のまま何でもCOMPLETEにしてよいわけではない。

次の2モードを区別する。

### development / scratch E2E mode

今回のscratch E2Eでは、`LOW_RISK_REVERSIBLE` な暫定判断のみであれば、人間確認を待たずに最後まで進めてよい。

ただしCOMPLETE時の結果には必ず

```text
COMPLETE_WITH_PROVISIONAL_DECISIONS
```

相当の明示的な補助情報を残すこと。

トップレベルState `COMPLETE` は増やさない。RunState/結果メタデータ等で表現する。

### normal / production mode

人間未承認のprovisional decisionが残っている場合、COMPLETE gateでblockする。

blocker例:

```text
UNAPPROVED_PROVISIONAL_DECISION
```

既存CompleteGateに追加する場合は、通常モードだけで有効にする。

## 6. Directorの役割を明確化する

今回の処理はReviewerやAnswererへ分散させず、Director責務としてまとめることを推奨する。

Directorは次を行う。

1. 正式成果物で回答可能か確認。
2. 回答不能なら未決定事項を分類。
3. LOW_RISK_REVERSIBLEなら暫定案を1つだけ選ぶ。
4. 高リスクならhuman batchへ積む。
5. 同じstageに他の未決定事項がないか、1回のbounded passで追加抽出する。
6. 追加抽出で無限に質問を増やさない。

ControllerはDirector出力をschema検証するだけで、意味判断しない。

---

## 7. 「止まらない」を優先しすぎない

次のケースは必ず停止する。

- セキュリティ/認証/秘密情報に関わる仕様未決定
- データ削除/不可逆migration
- 外部契約や公開API互換性
- 法令/顧客要求
- Workerが複数回同じ問題を繰り返す
- artifactの根拠が矛盾している
- CompleteGate blockerを迂回しないと進めない

目的は「止めないこと」ではなく、**意味のない1件ずつの往復をなくすこと**である。

## 8. Main Graph E2E再実行

実装後、まず通常pytestを全件実行する。

その後、新規scratch workspaceでCodex単独安定構成を優先してMain Graph実AI E2Eを行う。

前回と同等の小さなCLI仕様でよい。

期待する流れ:

```text
IDLE
-> DESIGN
   -> QUESTION
   -> Director classification
   -> LOW_RISK_REVERSIBLEなら provisional decision
   -> DESIGN継続
-> IMPLEMENT
-> TEST
-> REVIEW
-> DOC_SYNC
-> COMPLETE
```

今回の最優先成功条件は、**最初の軽微な仕様未決定でHUMAN_REQUIREDへ即停止しないこと**。

次に、実際に `IDLE -> COMPLETE` が1回通ること。

もし高リスク質問が自然発生した場合は、batchとして1回だけHUMAN_REQUIREDへ停止し、成功を演出しない。

## 9. テスト要件

少なくとも次を追加する。

1. artifactに答えあり -> DECIDABLE_FROM_ARTIFACT -> 自動回答して継続。
2. LOW_RISK_REVERSIBLE -> provisional decision保存 -> HUMAN_REQUIREDに即遷移しない。
3. provisional decisionがSQLite canonicalに保存される。
4. QandA.mdは生成物で、手編集しても判定は変わらない。
5. HIGH_RISK_PRODUCT_DECISION -> human batchへ積まれる。
6. SECURITY_OR_SAFETY -> provisional禁止。
7. 複数human questionsを1回のHUMAN_REQUIREDでまとめて提示。
8. answer-batchで複数回答後、各questionが正しいreturn positionへ戻れる。
9. scratch modeではLOW_RISK provisionalを残したままE2E継続可能。
10. normal modeでは未承認provisionalがCompleteGate blockerになる。
11. loop guard / NO_PROGRESS / WORKER_RESOURCE_LIMITの既存意味を壊さない。
12. トップレベルStateが10個のまま。
13. 通常pytestは外部AI不要。

## 10. 禁止事項

- `CANNOT_ANSWER` を無条件でPASSへ変換しない。
- 全質問をLOW_RISK扱いしない。
- Controllerに自然言語キーワード判定でrisk分類を書かない。
- 暫定判断を正式SPEC確定として扱わない。
- 人間未承認decisionをnormal modeでCompleteGateから隠さない。
- HUMAN_REQUIREDを削除しない。
- QandA.mdをcanonicalにしない。
- SQLiteを手編集してE2Eを通さない。
- SPECをE2E成功用に都合よく書き換えない。
- 4AI全参加をE2E成功条件にしない。まずCodex安定構成で1回完走を優先する。
