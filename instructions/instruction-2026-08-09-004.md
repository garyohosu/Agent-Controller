# Agent Controller 実装指示書 004

## 対象

`instruction-2026-08-08-001.md` §17-15 COMPLETE gate。

§17-14 Git checkpoint / rollback / Worker fallback は完了済みとする。

この指示では、Main Graph 全体をまだ実配線しない。
先に COMPLETE へ入るための出口条件を Controller 側で機械的に固定する。

---

## 目的

`COMPLETE` を AI の自己申告や単一の `PASS` Event だけで到達できる状態にしない。

Controller が実データを確認し、必要な条件をすべて満たした場合だけ `COMPLETE` へ遷移できるようにする。

狙いは、後で Main Graph の `DESIGN -> IMPLEMENT -> TEST -> REVIEW -> DOC_SYNC -> COMPLETE` を実配線した際に、途中状態・未同期・未push・未解決質問を誤って完了扱いしないこと。

---

## 絶対に崩してはいけない前提

`hikitsugi.md` の 5 原則を守ること。

1. Controller は意味を解釈しない
2. 遷移表はトップレベルと DocumentStage の 2 段を混ぜない
3. トップレベル State は 10 個から増やさない
4. SQLite が制御状態の正本、Markdown は投影・生成物
5. ループ停止は Controller の機械的 Guard、`recursion_limit` は非常停止装置

COMPLETE gate の判定に自然言語の内容理解を入れないこと。

---

# 1. COMPLETE gate の基本形

Controller に、現在の run が COMPLETE 可能かを機械的に判定する処理を実装する。

概念上は以下のような形でよい。

```python
CompleteCheckResult(
    ready: bool,
    blockers: list[CompleteBlocker],
)
```

`ready` は `blockers` が 0 件のときだけ `True` とする。

既に `human.complete_blockers()` 等が存在する場合は、責務が重複しないよう統合・再利用すること。

---

# 2. 必須 8 条件

最低限、以下をすべて Controller が確認すること。

## 2.1 必要な設計成果物が VALID

対象の DocumentStage について artifact status を SQLite から確認する。

最低限：

```text
SPEC
USECASE
SEQUENCE
CLASS
UI（計画対象の場合のみ）
TESTCASE
```

`STALE` または `REVIEW_REQUIRED` が残っている場合は COMPLETE 不可。

計画に含まれない UI 等を「存在しないから blocker」にしないこと。

判定は artifact table / plan 等の構造化情報から行い、Markdown 本文を読んで判断しない。

## 2.2 CODE latest

実装成果物が現行設計に対して最新であることを示す機械的状態を確認する。

まだ CODE artifact の status 管理が十分でない場合は、今回の実装範囲で最小限の構造化状態を追加してよい。

ただし自由文の「実装済みです」を根拠にしない。

今後 Main Graph の IMPLEMENT 実配線で更新できる形にしておくこと。

## 2.3 TEST PASS

最新のテスト結果が PASS であること。

過去の PASS があっても、その後 CODE / 設計が変更されているなら有効とみなさないこと。

可能なら「どの revision / artifact generation に対する PASS か」を比較できる構造を持たせる。

MVP では少なくとも「最新変更より後の TEST PASS」であることを機械的に判定する。

## 2.4 REVIEW PASS

最新の実装に対する Review が PASS であること。

TEST と同様、古い Review PASS を使い回さないこと。

AI の reason 文は判定根拠にしない。

## 2.5 QandA OPEN = 0

questions table を正本とし、`OPEN` が 0 件であること。

`QandA.md` を読み戻して数えない。

## 2.6 QandA HUMAN_REQUIRED = 0

`OPEN = 0` だけでは不十分。

人間待ちの質問が残っている run は COMPLETE 不可。

```text
OPEN = 0
HUMAN_REQUIRED = 0
```

を両方確認すること。

## 2.7 README latest / 更新不要判定済み

README を正式成果物として扱う。

次のどちらかが明示的に成立していること。

```text
README = latest
```

または

```text
README update = not required
```

「README を触っていないから多分不要」は不可。

SPEC_CHANGE / USECASE_CHANGE / 公開 CLI / API / 設定 / インストール方法 / ユーザー向け挙動変更があれば、将来 DOC_SYNC で更新対象になる形にしておくこと。

今回 Main Graph の DOC_SYNC 実配線までは不要だが、COMPLETE gate が必要とする構造化状態は定義してよい。

## 2.8 Git が確定状態

最低限以下を確認する。

```text
working tree clean
commit 済み
push 済み
```

### working tree clean

Git の実状態を確認する。
Worker の自己申告を信用しない。

### commit 済み

必要な成果物変更が未コミットでないこと。

### push 済み

ローカル HEAD が対応する upstream に push 済みであること。

可能なら `HEAD == upstream` 相当を Git の実情報で確認すること。

upstream 未設定等で確実に判定できない場合は COMPLETE 不可として blocker を返すこと。

# 3. Blocker は機械可読にする

単なる文字列リストだけにしない。

例：

```python
class CompleteBlockerCode(str, Enum):
    ARTIFACT_NOT_VALID = "ARTIFACT_NOT_VALID"
    CODE_NOT_LATEST = "CODE_NOT_LATEST"
    TEST_NOT_PASS = "TEST_NOT_PASS"
    REVIEW_NOT_PASS = "REVIEW_NOT_PASS"
    OPEN_QUESTION = "OPEN_QUESTION"
    HUMAN_REQUIRED_QUESTION = "HUMAN_REQUIRED_QUESTION"
    README_NOT_SYNCED = "README_NOT_SYNCED"
    GIT_DIRTY = "GIT_DIRTY"
    GIT_UNCOMMITTED = "GIT_UNCOMMITTED"
    GIT_NOT_PUSHED = "GIT_NOT_PUSHED"
```

名称は既存モデルとの整合に合わせて変更してよい。

Controller が判定に使うのは code / structured fields とし、人間向け detail は別に持てるようにする。

例：

```text
code=ARTIFACT_NOT_VALID
artifact=CLASS
status=STALE
```

# 4. COMPLETE 遷移の Guard

トップレベルの `DOC_SYNC -> COMPLETE` またはそれに相当する遷移で、gate を必ず通す。

単に Event.PASS を受けただけで COMPLETE に入れない。

概念：

```text
DOC_SYNC
  ↓ PASS
check_complete()
  ├─ blockers = 0 → COMPLETE
  └─ blockers > 0 → COMPLETE に入れない
```

既存遷移表の純粋性を壊さないこと。

`TRANSITIONS` 自体に自然言語や DB 判定を埋め込まず、遷移を適用する前後の Controller 層で gate を行う。

トップレベル State を追加しないこと。

---

# 5. blocker がある場合の扱い

今回の目的は「誤って COMPLETE に入れないこと」。

blocker ごとに高度な自動復旧 routing まで実装しなくてよい。

最低限：

- COMPLETE 遷移を拒否する
- blocker 一覧を取得できる
- 状態遷移ログまたは status 表示で人間が確認できる
- run を破壊しない

既存設計上明白な復帰先がある場合のみ、既存 Event / State へ戻してよい。

意味を Controller が推測して routing しないこと。

# 7. テスト

通常の `uv run pytest -q` は外部 AI CLI 非依存のままにする。

最低限、以下をテストすること。

## 正常系

8条件がすべて成立した場合のみ COMPLETE 可能。

## 各 blocker

少なくとも以下を個別に 1 つずつ崩し、COMPLETE 不可になることを確認する。

```text
artifact STALE
CODE not latest
TEST not PASS
REVIEW not PASS
OPEN questionあり
HUMAN_REQUIRED questionあり
README not synced / 未判定
Git dirty
Git not pushed
```

8条件だが Git は複数種類 blocker に分かれて構わない。

## 古い PASS を使わない

```text
TEST PASS
↓
CODE変更
↓
COMPLETE不可
```

および可能なら

```text
REVIEW PASS
↓
CODE変更
↓
COMPLETE不可
```

を確認する。

## QandA.md 非依存

`QandA.md` を手編集しても COMPLETE 判定が変わらないこと。
questions table が正本であることを維持する。

## Git 実状態

Worker の `files_changed` 自己申告ではなく、Git 実状態で dirty / pushed を判断していることをテストする。
