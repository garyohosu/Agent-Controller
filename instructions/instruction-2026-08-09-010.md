# 1. 最初に「実装要求トレーサビリティ表」を作る

`instruction-2026-08-08-001.md` の §1～§17、およびその後の追加要求を項目単位に分解し、最低限次の状態で分類する。

```text

PARTIAL
TEST_ONLY
DOC_ONLY
NOT_IMPLEMENTED
OBSOLETE
```

各項目について最低限以下を記録する。

```text
requirement_id

status
implementation_files
test_files
evidence
remaining_gap
```

この表は結果書
`instructions/result-2026-08-09-017.md`
に必ず含める。

### 判定ルール

- 実装ファイルがあるだけでは `IMPLEMENTED` にしない。
- stub / fake / ScriptedHandlerだけなら `TEST_ONLY` または `PARTIAL`。
- READMEに書いてあるだけなら `DOC_ONLY`。
- 実AI経路が要求されている箇所は、可能ならlive証拠も確認する。
- 古いresultに「未実装」と書いてあっても、後続commitで実装済みなら最新コードを正とする。
- 逆にREADMEに「実装済み」とあってもコードがstubなら未実装扱いにする。

# 2. 特に重点監査する箇所

## 2.1 Director中心ループ

当初仕様の中心ループは次だった。

```text
REVIEWER
  ↓ FAIL / QUESTION
DIRECTOR
  ↓ 修正指示
IMPLEMENTER
  ↓
TEST
  ↓
REVIEWER
```

現在、QUESTION分類・PROVISIONAL・QANDAは実装済みだが、
**REVIEW FAIL / LOCAL_FIX / SERIOUS_ISSUE等をDirectorが意味解釈し、Implementerへ具体的な修正Directiveを再発行する経路が本当にMain Graphで実配線されているか**を確認する。

確認項目:

- REVIEW FAILが単純にIMPLEMENTへ戻るだけになっていないか。
- Reviewerのfinding_code / finding_subject / reasonが次のImplementer directiveへ反映されるか。
- Directorが構造化修正指示を返し、Controllerがschema検証する責務分離になっているか。
- 自由文reasonをControllerが意味解釈していないか。
- 再TEST / 再REVIEWがfresh revisionに紐付くか。

不足があれば今回実装する。

---

## 2.2 DOC_SYNC / README自動同期

当初仕様ではREADMEは正式成果物であり、少なくとも次の場合に更新要否を判定する。

```text
SPEC_CHANGE
USECASE_CHANGE
公開API / CLI変更
設定方法変更
インストール方法変更
ユーザー向け動作変更
```

監査項目:

- `DOC_SYNC` が固定 `LATEST` / `NOT_REQUIRED` を受け取るだけになっていないか。
- README更新要否を誰が判定するのか。
- 更新が必要な場合、実際にWorkerがREADMEを書けるか。
- README変更後にreviewされるか。
- README artifact freshnessが現在CODE / design revisionに紐付くか。
- CompleteGateが古いREADME VALIDを誤利用しないか。

不足があれば、過度に複雑化せず最小の実配線を追加する。

推奨:

```text
DOC_SYNC
  ↓ Director/DocSync worker structured decision
NOT_REQUIRED → README VALID
UPDATE_REQUIRED → Implementer/Doc worker → review → README VALID
```

新しいトップレベルStateは追加しない。

---

## 2.3 Impact Analysis

現在のImpact Analysisが当初要求を満たしているか確認する。

最低限:

- AIが `VALID / REVIEW_REQUIRED / STALE` を提案
- Controllerが依存制約を機械検証
- 最上流の必要箇所から再開
- CODE / READMEまで影響対象
- 不正impact結果は適用しない
- 影響理由と再開理由をログへ残す

さらに、現在の依存関係が単純な一直線なら、MVP上許容するか、明らかな欠陥としてDAG化すべきかを判断する。

**将来拡張目的だけの大規模DAG実装はしない。**
ただしUIやCODE等に明白な誤依存があり、実動作を誤らせるなら最小DAGへ修正する。

---

## 2.4 Git checkpoint / rollback / Worker fallback

§17-14実装がMain Graph全経路で使われているか再確認する。

監査対象:

- DESIGN各mutating phase
- IMPLEMENT
- DOC_SYNCでREADME更新する場合
- Worker switch
- WORKER_ERROR
- WORKER_RESOURCE_LIMIT
- process timeout
- unexpected Worker commit
- push failure

確認事項:

- checkpointは実際の開始SHA
- rollbackはそのSHA
- untrackedを無条件`git clean -fd`しない
- failure後の次Workerは半端な差分を見ない
- push失敗ではvalid local commitを破壊しない
- `files_changed`はGit実状態で検証

既存テストだけでなく、配線漏れがないことを見る。

---

## 2.5 CompleteGate freshness

正常系E2Eが通っていても、古いPASSの再利用ができないことを再監査する。

最低限:

```text
Design VALID
CODE latest
TEST PASS fresh
REVIEW PASS fresh
Q&A blockers = 0
README latest / NOT_REQUIRED
Git clean
commit済み
push済み
unapproved provisional = 0（normal mode）
```

確認するケース:

- TEST PASS後にCODE変更 → block
- REVIEW PASS後にCODE変更 → block
- README VALID後にCLI/API変更 → block
- provisional decision追加 → normal mode block
- push失敗 → block

# 5. テスト

今回追加・確認すべきテスト候補:

1. REVIEW FAIL → Director修正指示 → IMPLEMENT → TEST → REVIEW PASS
2. Reviewer findingが次Implementer directiveへ渡る
3. DOC_SYNC NOT_REQUIRED
4. DOC_SYNC UPDATE_REQUIRED → README変更 → review → VALID
5. README freshness invalidation
6. CODE変更後の古いTEST PASS拒否
7. CODE変更後の古いREVIEW PASS拒否
8. Impact AnalysisでCODE/README STALE
9. Worker fallbackでcheckpoint保持
10. push failure時CompleteGate block
11. normal modeでPROVISIONAL block
12. scratch modeだけprovisional許可
13. 本番Main Graphにstub handlerが混入していない

既存テストで十分な場合は重複テストを増やさず、そのテストID/ファイルを結果書へ記録する。

```text

→ DESIGN
```

Codex-only安定構成でよい。

ただし、期待Eventを出させるために入力を何度も改変してはいけない。

4AI全員でE2E完走することは今回の必須条件ではない。

# 7. 完了判定

今回の最終判定は次のどれかとする。

```text
AUDIT_COMPLETE_NO_GAPS
AUDIT_COMPLETE_GAPS_FIXED
RESULT_PRODUCED_WITH_LIMITATIONS
```

### AUDIT_COMPLETE_NO_GAPS

要求トレーサビリティ上、MVP必須項目に未実装がない。

### AUDIT_COMPLETE_GAPS_FIXED

不足を発見したが今回すべて修正し、テストと必要なE2Eを通した。

### RESULT_PRODUCED_WITH_LIMITATIONS

高リスク仕様未決定、実環境制約等により残件がある。
残件を具体的に列挙する。

単に「E2EがCOMPLETEした」だけでAUDIT_COMPLETEにしない。

# 9. Git

作業開始時:

```text
git status --short
git pull --ff-only origin main
```

終了時:

```text
uv run pytest -q
git diff --check
git status --short
git add -- <必要ファイルのみ>
git commit
git push origin main
git rev-parse HEAD
git rev-parse origin/main
git status --short
```

`git add .` / `git add -A` / force pushは禁止。

結果書を含めてcommit / pushし、

```text
HEAD == origin/main
working tree clean
```

まで確認して完了すること。

---

## 最重要方針

今回の仕事は「もう動いたから完成とみなす」ことではない。

**仕様要求 → 実装 → テスト → 実AI証拠を最後に一本化し、抜けがあればその場で埋めること。**

1件ずつ止まらず、最後まで監査・修正・検証を進めること。
