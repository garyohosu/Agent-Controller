## 実施内容

AI に「これは無限ループか」を判定させず、Controller が機械的な上限を持つようにした。

歯止めは 2 種類ある。

| 種類 | 見るもの | 判定 |
|---|---|---|
| 回数の上限 | 何回繰り返したか | 純関数（`check_counters`） |
| NO_PROGRESS | 同じ失敗が繰り返されているか | 指紋の履歴（`NoProgressTracker`） |

歯止めが働くと Event を返し、呼び出し側がそれを **1 遷移として記録する**。
つまり「起きたこと」と「歯止めが働いたこと」は別の行としてログに残る。
順序も固定していて、先に起きたことを記録し、後から歯止めを見る。
逆にすると実際に起きた遷移がログから消える。

`recursion_limit` は指示どおり最後の非常停止装置として残した。
通常のループ停止は guard が行う。

## カウンタの分離

指示のとおり `retry=` を 3 つに分けた。**別名は残していない**（全面改名）。

```text
state_retry   同じトップレベル State を続けて実行した回数
review_retry  現在の Document Stage で FIX からレビューへ戻った回数
repeat        直前とまったく同じ遷移が続いた回数
```

`repeat` は初回 0、2 回目で 1（連続した「余分な」回数）。
これにより、正常に進んでいる行にはカウンタが 1 つも出ない。

### ログの形

カウンタ行を独立させた。

```text
20:33:13 | DESIGN/CLASS/REVIEW_LIGHT | LOCAL_FIX
         -> DESIGN/CLASS/FIX | worker=CODEX_CLI | role=REVIEWER | reason=class naming mismatch
         | review_retry=2
```

**3 行目は、いずれかのカウンタが 0 でないときだけ出す。** 全部 0 の行は 2 行のまま。
正常系のログが 1.5 倍に膨らむのを避けるための判断で、指示にあった形からの逸脱は
ここだけ。不要なら `render_transition` の 1 箇所で戻せる。

値が 0 のカウンタは表示しない（`state_retry=0` は書かない）。

## 実装した歯止め

### 回数の上限（`GuardLimits`）

| 設定 | 既定 | 超えたときの Event |
|---|---|---|
| `max_upstream_rework` | 3 | `LOOP_DETECTED` |
| `max_same_transition` | 3 | `LOOP_DETECTED` |
| `max_state_retry` | 5 | `RETRY_LIMIT` |
| `max_total_transitions` | 500 | `LOOP_DETECTED` |
| `max_same_fingerprint` | 3 | `NO_PROGRESS` |

`max_review_retry` だけは stage ごとに変えたいので `DocumentStageConfig` 側に残した
（指示書 §3 の設定例のまま）。超えると `RETRY_LIMIT`。

Event の割り当ては、**回数の超過は `RETRY_LIMIT`、同じところを回り続けているのは
`LOOP_DETECTED`、同じ失敗が直らないのは `NO_PROGRESS`** で分けた。
トップレベルの遷移表では 3 つとも `HUMAN_REQUIRED` へ行くが、ログには区別が残る。

### 判定の順序

複数同時に超えることがあるので順序を固定した。具体的な事象を表すものを先に置く。

```text
1. Worker を替えても同じ失敗          -> NO_PROGRESS
2. 同じ失敗の繰り返し（回数超過）      -> NO_PROGRESS
3. 上位手戻りの回数超過               -> LOOP_DETECTED
4. 同一遷移の連続                    -> LOOP_DETECTED
5. State の連続実行                  -> RETRY_LIMIT
6. 1 run の総遷移数                  -> LOOP_DETECTED
```

最初に一致したものを返す。

### NO_PROGRESS

指紋は `(state, substate, phase, event, reason)` から作る。
数えるのは**問題を表す Event だけ**で、`PASS` や `DONE` は数えない
（進んでいるだけなので意味がない）。

```text
FAIL  LOCAL_FIX  QUESTION  SERIOUS_ISSUE  UPSTREAM_CHANGE_REQUIRED  WORKER_ERROR
```

指紋ごとに担当した Worker を覚えておき、**Worker を替えても同じ失敗が出たら
回数を待たずに人間へ渡す**（§11）。Worker の調子ではなく仕様か設計の問題だから。

## 「中断」はループではない

`WORKER_RESOURCE_LIMIT` / `RESOURCE_AVAILABLE` / `HUMAN_ANSWER` は
`state_retry` も `repeat` も増やさない。直前の遷移としても記録しない。

rate limit を 3 回待っただけの run は同じところを回っているわけではない。
これを数えると、辛抱強く待った run が `LOOP_DETECTED` で止まってしまう。

同じ理由で、stage の開始時（`START` 行）に `last_transition_key` をクリアしている。
stage をまたいで `repeat` が繋がらないようにするため。stage のやり直しそのものは
`upstream_rework` が数える担当。

## 呼び出し箇所

Controller の driver は 3 つあり、いずれも遷移を記録した直後に guard を呼ぶ。

```text
graph.py           Main Graph の node
document_stage.py  Document Stage の phase node
design.py          DESIGN の stage ループ
```

driver ごとに「歯止めが働いて HUMAN_REQUIRED へ行く」テストを 1 本ずつ置いた。
呼び忘れた driver があれば落ちる。

`run_design` は guard を渡さなくても既定の `LoopGuard` を使う。歯止め無しでは回さない。

## 状態遷移ログ例

同じ指摘が直らず `NO_PROGRESS` で人間へ渡るまで（UTC 表示、中略）:

```text
20:33:13 | DESIGN | START
         -> DESIGN/CLASS/GENERATE | checkpoint=357c5d5
20:33:13 | DESIGN/CLASS/GENERATE | DONE
         -> DESIGN/CLASS/REVIEW_LIGHT | worker=CLAUDE_CODE | role=IMPLEMENTER | checkpoint=357c5d5
20:33:13 | DESIGN/CLASS/REVIEW_LIGHT | LOCAL_FIX
         -> DESIGN/CLASS/FIX | worker=CODEX_CLI | role=REVIEWER | checkpoint=357c5d5 | reason=class naming mismatch
20:33:13 | DESIGN/CLASS/FIX | DONE
         -> DESIGN/CLASS/REVIEW_LIGHT | worker=CLAUDE_CODE | role=IMPLEMENTER | checkpoint=357c5d5
         | review_retry=1

  （同じ往復が 2 回続く。review_retry が 2、3 と増える）

20:33:13 | DESIGN/CLASS/REVIEW_LIGHT | LOCAL_FIX
         -> DESIGN/CLASS/FIX | worker=CODEX_CLI | role=REVIEWER | checkpoint=357c5d5 | reason=class naming mismatch
         | review_retry=3
20:33:13 | DESIGN/CLASS/FIX | NO_PROGRESS
         -> HUMAN_REQUIRED/CLASS | worker=CODEX_CLI | role=REVIEWER | checkpoint=357c5d5 | reason=LOCAL_FIX at DESIGN/CLASS/REVIEW_LIGHT repeated 4 times > 3
         | review_retry=3
```

最後の行だけが歯止めで、それまでは実際に起きたことがそのまま残っている。
理由文に「どの Event が、どの位置で、何回」が入っているので、
歯止めの行だけ読めば何が直らなかったか分かる。

なお、この例では `repeat` は最後まで 0 のままである。
`REVIEW_LIGHT → FIX` と `FIX → REVIEW_LIGHT` は別の遷移なので「同一遷移の連続」には
当たらない。往復の検出は `repeat` ではなく指紋の担当という分担になっている。

### 制約・注意点

1. **指紋の質は Worker の理由文の書き方に依存する。** 今は
   `(state, substate, phase, event, reason)` を小文字化・トリムして突き合わせるだけ。
   実 AI Worker が自由記述で書くようになると「2 tests failed」と「2 failing tests」が
   別物になり、`NO_PROGRESS` が働かなくなる。正規化が要るかもしれない（§17-12 の論点）。
   逆に、reason を空にすると位置と Event だけで同一視されるので過検出になる。
2. **`state_retry` と `upstream_rework` は DESIGN 中に重なって増える。**
   上位手戻りは `DESIGN -> DESIGN` の自己ループでもあるため、両方が数える。
   順序で `upstream_rework`（具体的）を先に見るようにしてあるので、
   実際には `LOOP_DETECTED` が先に出る。既定値も `max_upstream_rework`(3) <
   `max_state_retry`(5) にしてある。
3. **歯止めの行の「位置」は遷移した後の位置になる。** 上の例で
   `DESIGN/CLASS/FIX | NO_PROGRESS` となっているのは、`LOCAL_FIX` を記録して
   FIX へ移った直後に guard を見ているため。元の失敗の位置は理由文に入れてある。
4. **`EXIT` の名前は据え置き。** ESCALATE 系に寄せる案は引き続き保留。
5. **新カラムのマイグレーション経路は無い。** `runs` のカウンタ改名、
   `transitions` のカウンタ 3 分割、`fingerprints` テーブル追加はいずれも
   `CREATE TABLE IF NOT EXISTS` のみ。既存 `.db` があると壊れる。
   実 DB はまだ無い（gitignore 済み・テストは `:memory:`）ので今は無害だが、
   AI Worker を接続して実運用の DB ができる前に片付ける必要がある。
6. **`max_total_transitions` は run 全体の総数で、リセットされない。** 長期間の run では
   正常でも到達しうる。500 という既定値は根拠のある数字ではない。
