## 実施内容

§17-7 を実装し、§17-8 の初期配線を同時に入れた。

```text
SPEC → USECASE → SEQUENCE → CLASS → (UI) → TESTCASE → DESIGN+PASS → IMPLEMENT
```

保つよう指示された 2 つの性質は、テストで直接確認している。

- **stage 内は局所処理** — 設計全工程を通して `to_state` は `DESIGN` のまま。
  変わるのは最後の 1 行（`DESIGN + PASS -> IMPLEMENT`）だけ。
- **stage を抜ける時だけ上位へイベントを返す** — `EXIT` した Event だけが
  トップレベルの遷移表を引く。

`design.py` は LangGraph ではなく素の Python ループにした。やっているのは
「次にどの stage を回すか」の選択だけで、graph にするほどの分岐が無いため。
stage 単位の移動も必ず logger を通すので、遷移ログからは同じように追える。

## 前回指摘の 3 点への対応

| 指摘 | 対応 |
|---|---|
| WAIT_RESOURCE からの再開で phase が失われる | **今回実装した。** `RunState.return_phase` を追加（`return_state` の phase 版）。レビュー途中で止まった stage は `GENERATE` からやり直さず、止まった phase から再開する |
| `REVIEW_DEEP + SERIOUS_ISSUE -> EXIT` は妥当。EXIT を ESCALATE 系に寄せると分かりやすいかも | **未対応（次の設計の論点として記録）。** 今回は `ESCALATING_EVENTS` という名前で「上位へ戻す離脱」と「同じ場所へ戻ってくる中断」を内部的に区別するところまで。Event 名の変更はしていない |
| `retry=` の意味が二重（`state_retry` / `review_retry` / `transition_repeat` に分ける） | **未対応（§17-9）。** 今回もログ上で二重のまま。下の「制約」に実例を残した |

### return_phase の設計判断

**残すのは「同じ場所へ戻ってくる中断」だけにした。**

```python
ESCALATING_EVENTS = {UPSTREAM_CHANGE_REQUIRED, SERIOUS_ISSUE}
```

- `WORKER_RESOURCE_LIMIT` / `WORKER_ERROR` / `CANNOT_ANSWER` / `RETRY_LIMIT`
  → `return_phase` を残す。同じ stage の同じ phase へ戻る
- `UPSTREAM_CHANGE_REQUIRED` / `SERIOUS_ISSUE`
  → 残さない。上流が変わる以上その stage はやり直しになるため、
  途中から再開すると古い前提のまま進んでしまう

**`review_retry_count` は中断をまたいで保持する。** リセットすると、thrash している
stage が resource limit を挟むだけで `RETRY_LIMIT` を回避できてしまう。
これは §17-9 が気にする種類の相互作用なので、今のうちに閉じた
（`test_resume_keeps_the_review_retry_budget`）。

## 上位工程への手戻り

`UPSTREAM_CHANGE_REQUIRED` で戻り先を決めるにあたり、**Controller は推測しない**方針にした。

- `StageResult.upstream_target` を Worker が指定する。指定が無ければ
  `MissingUpstreamTargetError` で拒否する（「1 つ上の工程だろう」と補完しない）
- 指定された工程とその下流を `STALE` にし、最上流の `STALE` から再開する

**この影響範囲判定は暫定である。** 指示書 §6 の IMPACT_ANALYSIS は成果物ごとに
`VALID` / `REVIEW_REQUIRED` / `STALE` を評価するが、それは §17-10。
今は「上流が変われば下流は全部やり直し」という最も粗い規則しか無い。
`REVIEW_REQUIRED` は一度も付かない。

実際の効果は確認できている。CLASS のレビューが SEQUENCE を指した場合、
再実行されるのは SEQUENCE と CLASS だけで、SPEC と USECASE は触らない
（§2 の「必要最小限の上位工程へ戻す」）。

なお round 1 で作った `artifacts` テーブルを、ここで初めて実際に使った。

## 未実装事項 / 制約

### 次の chunk 以降

- **§17-9 loop guard** — 実装したのは `max_review_retry` による `RETRY_LIMIT` と、
  DESIGN ループ専用の `max_upstream_returns` による `LOOP_DETECTED` だけ。
  `same_transition_count`、`no_progress_fingerprint`、1 run の最大 transition 数、
  「Worker を替えても同一失敗」は未実装。
- **§17-10 IMPACT_ANALYSIS** — 上記のとおり判定は暫定。`REVIEW_REQUIRED` が付かない。
- §17-11 以降（Worker interface、adapter、QandA.md 実体、Git checkpoint / rollback、
  README / COMPLETE gate）は未着手。
- **Main Graph との接続はまだ。** `graph.py` の DESIGN node は stub のままで、
  `run_design` を呼んでいない。§17-11 の Worker interface と合わせて配線するのが自然。

### 制約・注意点

1. **`retry=` の意味が依然として二重。** 上のログ例の
   `UPSTREAM_CHANGE_REQUIRED` 行にある `retry=1` は `RunState.retry_count`
   （DESIGN → DESIGN の自己ループ回数）で、stage 内の行の `retry=` は
   `review_retry_count`。§17-9 で `state_retry` / `review_retry` /
   `transition_repeat` に分ける。
2. **`EXIT` は「終了」ではなく「上位へ返す」の意味で使っている。** 名前として
   `ESCALATE` 系に寄せる案は次の設計の論点として保留。
3. **新カラムのマイグレーション経路は無い。** `runs` に `return_phase` と
   `pending_upstream_stage` が増えたが、`CREATE TABLE IF NOT EXISTS` しか無いため、
   前のコミットで作った `.db` があると `save_run` が落ちる。
   実 DB がまだ存在しない（gitignore 済み・テストは `:memory:`）ので今は無害。
4. **stage をまたいだ DEEP 昇格の持ち越しは無い。** 002 から変わらず、
   次の stage に入ると `review_level` の初期値に戻る。
5. **`upstream_target` は計画に含まれる工程しか指せない。** UI を計画から外している
   場合に UI を指すと `ValueError`。Worker への指示にどの工程が有効かを渡す必要がある。
6. `run_design` は同期ループで、1 stage ずつ直列に回す。並行実行は考えていない。
